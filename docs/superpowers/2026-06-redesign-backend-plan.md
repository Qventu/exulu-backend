**Written:** 2026-06-16
**Audience:** backend engineer(s) picking up the tickets

The frontend ships with honest-degradation states for every backend gap, so nothing here is a production blocker. But several tickets unlock features the UI is already wired for, and **BE-2(a) is a data-integrity audit that should land first regardless of the rest of the schedule.**

## 0. Quick orientation

- Backend source: `backend/src/exulu/` (LiteLLM glue, REST routes) + `backend/src/graphql/` (auto-generated GraphQL types from table metadata) + `backend/src/postgres/` (schema definitions)
- GraphQL pattern: tables defined in `postgres/core-schema.ts` and others; types/inputs/resolvers auto-generated by `graphql/schemas/index.ts`, `graphql/mutations/index.ts`, `graphql/resolvers/index.ts`. To expose a new field on an existing type, edit the table definition + the type-builder block (e.g. `schemas/index.ts:90-120` is where computed fields like `budget: JSON` get appended per singular).
- `xByIds` resolvers (`agentByIds`, `userByIds`, `projectByIds`, `workflow_templatesByIds`) appear to be auto-generated from the same machinery — adding a new one means adding the table to the right loop, not hand-writing a resolver.
- Schema migrations: no formal migrations folder. New tables get added in `init-exulu-db.ts`. Existing-table ALTERs happen ad-hoc or via deploy scripts — **confirm the deploy process with team before adding columns**.

## 2. Per-ticket detail

### BE-2 — Variable value-on-demand semantics ⚠️ DO THIS FIRST

**Status:** **confirmed data-corruption hazard.** Investigation today:
- `src/graphql/utilities/encrypt-sensitive-fields.ts` AES-encrypts `input.value` whenever `input.encrypted === true && input.value` is truthy
- Three decrypt sites (`resolve-model.ts:273`, `routes.ts:406`, `embedder.ts:164`) — all in **consumers**, not the GraphQL resolver
- The GraphQL `variable.value` field returns the **stored ciphertext** as-is for encrypted variables
- Pre-redesign, the edit form fetched `value` on mount → user clicked Save → mutation re-encrypted the ciphertext → **double-encrypted blob in DB**
- The 4.5 redesign (`ccc9a33`) stopped auto-fetching the value and omits `value` from the update payload when unchanged — **no new corruption since 4.5 deployed**, but existing data may already be corrupted

**Two sub-tickets:**

#### BE-2(a) — DATA AUDIT (~½ day)
- Query: every variable where `encrypted = true` AND `updatedAt > createdAt + 1 minute` (rough "has been edited at least once after creation")
- For each, try `CryptoJS.AES.decrypt(value, NEXTAUTH_SECRET).toString(CryptoJS.enc.Utf8)` once — successful UTF-8 = single-encrypted; empty/garbage = double (or triple) encrypted
- Report by user/owner so they can rotate the secret manually (we cannot recover the plaintext — only flag and ask for re-entry)
- **Acceptance:** report of N corrupted variables + owner list emailed/Slacked to platform team
- **Files:** new one-off script under `backend/scripts/audit-variable-encryption.ts`; uses existing `CryptoJS` + DB connection

#### BE-2(b) — MUTATION CONTRACT DECISION (~½ day, after 2a)
Two options, pick one:
- **Option A (recommended):** update `encrypt-sensitive-fields.ts` to be a no-op when `value` is **omitted** from the input (today: only checks `input.value` truthy — already correct, just confirm). Frontend already sends `undefined` when value unchanged; this is the current contract. **No code change needed if the audit confirms the current behavior is correct.**
- **Option B:** add an explicit `valueChanged: Boolean` input field on `UPDATE_VARIABLE` for safety. Frontend sets it explicitly. More verbose but unambiguous.
- **Acceptance:** documented contract in `encrypt-sensitive-fields.ts` header (whichever option); frontend ticket (~10 min) to add `valueChanged: true` if Option B

**What:** Add `used_by: [String]!` + `used_by_count: Int!` to the GraphQL `variable` type. Each entry is `"{type}/{id}"` (e.g. `"agent/abc123"`).

**Scan sources:**
| Type | Storage | Match | Emitted as |
|------|---------|-------|-----------|
| Users with anthropic_token | `users.anthropic_token` column | by variable id | `"user/<id>"` |
| Agents referencing variables in config | `agents.config` JSON (referenced **by name**) | substring or JSONPath; document as **heuristic** ("referenced in configuration") | `"agent/<id>"` |

| Models | OUT OF SCOPE post-4.2 (custom-models deleted). If LiteLLM YAML references Exulu variable names, that's a config-time concern, not a resolver concern. Confirm with team. | — | — |

**Acceptance:**
- `variable { used_by, used_by_count }` populated correctly for all variable types
- Heuristic agent matches labeled as `"referenced in configuration"` in the resolver doc-comment (so frontend can render the right hint)
- Performance: scan happens lazily per query (not on every variable fetch — frontend only requests it on the detail panel + the table column)

**Frontend cleanup once shipped:**
- `app/(application)/variables/components/feedback-list.tsx` and `usage-list.tsx` already wired to render real `used_by` — drop the "Usage unavailable" honest-degradation copy

### BE-11 — Batched `GET_JOB_RESULTS` for the run matrix

**What:** Either:
- **(a)** Accept `OR` semantics over labels on the existing `GET_JOB_RESULTS` query, so the matrix can issue one query like `WHERE label CONTAINS ('eval-run-A' OR 'eval-run-B' OR ...) AND label CONTAINS '{case_id}'`
- **(b)** New resolver: `eval_run_results(run_ids: [ID!]!): { run_id: ID, results: [JobResult] }[]` — returns per-run buckets

**Pick (b)** — cleaner contract, same data, no SQL gymnastics on the frontend.

**Critical preservation:** the label semantics drive the per-cell lookup. The new resolver must either:
- Return job_results keyed by run_id, with `test_case_id` exposed as an explicit field (currently buried in the `label` string)
- OR preserve the `label contains "eval-run-{id}" + label contains "{test_case_id}"` shape so existing frontend cell-matching logic still works

**Acceptance:** matrix issues one query instead of N; data shape allows the existing ScoreCell rendering.
**Effort:** ~3-5 days. Largest open question is the label-vs-explicit-fields decision.

## 5. Risk callouts

1. **BE-1 heuristic agent matches** — substring matching against agent config JSON can over-match (e.g. variable name `KEY` matches anything containing "KEY"). Use structured matching where possible (key-value lookups in known config shapes), substring only as a fallback. Label the result as "referenced in configuration" so the user knows to verify.

2. **BE-10 performance** — the per-set aggregate runs on every /evals list page render. For installations with hundreds of eval sets + many runs each, the JOIN to `eval_runs` + `job_results` could be slow. Consider:
   - Materialized view refreshed every 60s
   - Cache layer with invalidation on RUN_EVAL / DELETE_EVAL_RUN / UPDATE_TEST_CASE
   - Or accept the query cost and add an index on `(eval_set_id, finishedAt DESC)` for last_run lookup

3. **BE-11 label-vs-explicit-fields** — the current label string format is the de-facto contract between the eval runner and the job-results storage. Changing it requires a coordinated update of both producers (eval runner) and consumers (frontend matrix). Prefer Option (b) — new resolver that returns per-run buckets without disturbing the existing label format.

4. **BE-2 audit findings** — if N is large (>~50 corrupted variables), need a UX strategy for affected users beyond "rotate manually": maybe a banner on `/variables` listing affected entries, or an email rollup.

5. **BE-7 RBAC scoping** — the `feedback:read` filter ("only see feedback for my own agents") needs to handle agent ownership transfers gracefully. If an agent moves between users, what happens to historical feedback visibility? Confirm policy before implementing.
