# LiteLLM 1.85.1 → 1.97.0 upgrade

**Date:** 2026-08-19
**Branch:** `chore/litellm-1.97` (off `develop`)
**Scope:** version bump and verification only. No adoption of new LiteLLM features.

## Goal

Move the pinned LiteLLM proxy from 1.85.1 to 1.97.0 (twelve minor releases,
2026-05-20 → 2026-08-15) without regressing the integration, and prove it
locally before anything ships.

## How LiteLLM is wired in

LiteLLM is not a library we import. It is a Python process the backend spawns
and supervises:

- `src/exulu/litellm/supervisor.ts:168` spawns
  `ee/python/.venv/bin/litellm --config <path> --port <port> --host <host>`
- Readiness is the unauthenticated `GET /health/liveliness`
  (`supervisor.ts:97`), polled every 200 ms with a 90 s boot budget
- The venv at `ee/python/.venv` is **shared** with the Whisper/docling ML stack
  and with our own FastAPI transcription server
- `ee/python/requirements.txt:34` holds the pin

The backend depends on LiteLLM through four narrow surfaces:

| Surface | Files | Depends on |
|---|---|---|
| Model catalog | `litellm/catalog.ts` | `GET /model/info` → `data[].model_name`, `litellm_params.model`, `model_info.*` |
| Tag budgets | `litellm/admin-client.ts`, `budget-service.ts` | `/tag/new`, `/tag/update`, `/tag/list`, `/tag/info`, `/tag/delete`, `/budget/update` |
| Usage analytics | `litellm/activity-client.ts`, `usage-view.ts` | `GET /tag/daily/activity` → `results[].breakdown.entities[tag].metrics` |
| Inference passthrough | `routes.ts`, `tags.ts`, `resolve-reranker.ts` | `/v1/*` with `x-litellm-tags` + `x-litellm-spend-logs-metadata` |

The backend never queries LiteLLM's Postgres tables directly. It does run
`prisma db push` against LiteLLM's bundled schema at boot
(`litellm/db-init.ts`), behind a safety gate that refuses to push into a
database containing non-`LiteLLM_*` tables.

## Breaking changes: triage

Ruled out by inspecting our code, not by assumption:

| Release-note breaking change | Why it does not apply |
|---|---|
| `/key/list` exact matching (1.90) | Never called; `passthrough-allowlist.ts:9` explicitly blocks `/key/*` |
| `deployment_affinity` defaults on (1.97) | Auto-router only; no `auto_router` model group in our config |
| `mock_*` params now 400 (1.96) | Not used |
| `stream_timeout` enforced on `/v1/messages` (1.94) | No `stream_timeout` set anywhere |
| `permissions`/`allowed_routes` admin-gated (1.92) | We do not call `/key/update`, `/user/new` |
| `skip_user_budget_on_team_key` removed (1.95) | Not present in config |
| `/v1/models` token limits re-sourced (1.93) | We read `/model/info`, not `/v1/models` |
| `/customer/daily/activity` admin-only (1.90) | Not called |

Applies, and must be verified:

1. **Tag-filtering routing** (1.94 #33436 changed how `enable_tag_filtering`
   from team/key applies to tag routing). The reference config sets
   `router_settings.enable_tag_filtering: True` and registers the *same*
   `model_name` three times — once per tenant (ADX / CX / SC) — distinguished
   only by `litellm_params.tags` and a different Vertex project. Tag routing is
   the tenant isolation boundary. A regression here misroutes one tenant's
   traffic to another's GCP project. Highest-severity item.
2. **Wildcard model names** (1.91 #31444 "restored wildcard expansion" on
   `/v1/model/info`). The config registers `claude-opus-5*`, `claude-sonnet-5*`
   etc.; `catalog.ts:96` strips the trailing `*`. If expansion now returns
   concrete names, the catalog's shape and the dedup keyed on
   `model_name`+`upstream_model` (`catalog.ts:121`) both change.
3. **`budget_reset_at` recomputed when `budget_duration` changes** (1.90
   #30555). Our sequence — `/tag/update` deliberately omitting the field
   (`admin-client.ts:68-75`), then `/budget/update` setting it
   (`admin-client.ts:89`) — means our explicit value still lands last and wins.
   This is the exact bug class we already shipped a fix for, so it needs a
   regression assertion rather than trust.
4. **Prisma schema growth** (54 KB → 60 KB; new `dcr_bridge`, `oauth2_flow`,
   `LiteLLM_DailyGatewayRequests`). `setup.sh` step 6.5 `prisma generate` must
   still succeed with `prisma` pinned at 0.15.0, and the `db-init.ts` safety
   gate must still hold.
5. **Over-budget keys are throttled, not revoked** (1.93 #31300). Changes what
   a budget-exceeded response looks like.
6. **`expose_router_debug_in_errors`** (1.90 #30418) — **no action; no
   regression.** Verified against the 1.97.0 wheel rather than the release
   notes, which are easy to read backwards. It is a `litellm_settings` key
   (module attribute `litellm.expose_router_debug_in_errors`), and it defaults
   to `True`, which *preserves historical behavior*: the router keeps appending
   `model_group`, fallback groups and deployment timeouts onto exception
   messages (`router.py:6397`). Nothing starts being redacted on upgrade, so the
   known "tag error masks a 429" diagnosis stays exactly as easy as today.
   LiteLLM documents an intent to flip this default to `False` in a future major
   release; at that point we get a real decision — diagnosability versus not
   disclosing internal model wiring to passthrough clients. Worth watching, not
   worth pre-empting.
7. **`store_prompts_in_spend_logs` YAML now beats DB** (1.97 #35769). The
   config sets it `true`, so prompt capture stays on and becomes authoritative
   from YAML. Relevant to the Value Ledger work.
8. **Error-code shifts**: Anthropic context overflow 500 → 400 (1.89); a
   mid-stream upstream reset now surfaces as an error instead of an empty 200
   (1.94); generic `error` finish reason maps to `stop` (1.97).
9. **`litellm_settings.request_timeout` is per-attempt** since 1.91. The config
   sets 600 s with `num_retries: 3`, so worst-case wall time is now ~3×600 s.
   Benign, but the documented semantics changed.

## Verification

Ordered so the cheapest, highest-signal checks fail first. Local only.

**The unit tests mock HTTP.** Passing jest proves we did not break our own
code; it does **not** prove LiteLLM's responses still match our parsers. Only
steps 5–7 establish that. Step 7 is the point of this plan.

1. `pip install -r ee/python/requirements.txt` resolves and installs
2. `prisma generate` against the grown schema — `setup.sh` step 6.5
3. `pytest ee/python/transcription/tests` — the only code crossing the
   Starlette 1.0 boundary
4. `npm test` — the 8 LiteLLM suites (`env`, `catalog`, `usage-view`,
   `activity-client`, `admin-client`, `supervisor`, `parse-reranker-models`,
   `passthrough-allowlist`)
5. Boot the proxy against the reference config at
   `/Users/daniel.claessen/Desktop/Projects/ai.open/config.litellm.yaml`;
   confirm `GET /health/liveliness` returns 200 within the 90 s budget
6. `prisma db push` against a scratch Postgres; confirm the new tables apply
   and the `db-init.ts` gate still refuses a database holding foreign tables
7. Live shape checks against the running proxy:
   - `GET /model/info` — capture output on 1.85.1 **before** upgrading, diff
     against 1.97.0, and assert `catalog.ts`'s parser produces the same entry
     set. Specifically covers wildcard expansion of `claude-opus-5*` and the
     three-tenant dedup.
   - Tag routing — issue the same `model_name` with `team_name_adx` vs
     `team_name_cx` tags and confirm each lands on its own Vertex project.
     This is the tenant-isolation check.
   - Budget round-trip — `/tag/new` → `/budget/update` → `/tag/info`, asserting
     `budget_reset_at` survives and matches what we set.
   - `GET /tag/daily/activity` — confirm the `breakdown.entities[tag].metrics`
     nesting `usage-view.ts:108` expects.
   - `POST /v1/rerank` — confirm `results[].index` and
     `results[].relevance_score`, which `resolve-reranker.ts:84` reads with no
     fallback.

Capture the step-7 "before" artifacts while still on 1.85.1; they are worthless
after the upgrade.

## Rollback

Restore `1.85.1` in `requirements.txt` and re-run `pip install -r`. Because
only 16 small packages move and none are the multi-GB ML wheels, this is a
sub-minute operation — no `npm run python:rebuild`, no re-download of torch.
This cheap rollback is why the upgrade is done in place in the primary checkout
rather than in an isolated venv.

## Out of scope

Deliberately excluded, recorded so they are not lost:

- Adopting `litellm_call_id` on spend logs (1.91) and the new
  `LiteLLM_DailyGatewayRequests` table (1.97) for the Value Ledger and
  artifact-to-session tracing
- Defensive handling for throttle-vs-revoke (1.93) and the new error codes
- Deciding on `expose_router_debug_in_errors`. Deliberately deferred: the
  default is unchanged by this upgrade, so there is nothing to fix now. Revisit
  when LiteLLM flips it to `False` in a future major.
- New features otherwise unlocked: SSE keepalives on `/v1/messages`,
  caller-scoped spend reports, `/management/v1/budgets`, admin viewer parity,
  SAML SSO, guardrail `scan_only_tool_results`

One 1.97.0 fix is worth flagging as a latent bug already resolved: **custom
`model_info` is now preserved across a price reload** (#35491). We depend on
custom `model_info.type`, `dimensionality`, `sizes` and `max_batch_size`, all of
which could previously be clobbered when LiteLLM reloaded its price data.

## Verification result

Verified locally on 2026-08-19 against the reference config at `ai.open/config.litellm.yaml`. All checks ran on `chore/litellm-1.97`.

### Passed

Dependency resolution: 16 packages changed as predicted. Every load-bearing ML pin held — `torch 2.5.1`, `torchaudio 2.5.1`, `torchvision 0.20.1`, `transformers 4.57.6`, `huggingface_hub 0.36.2`, `tokenizers 0.22.2`, and `prisma 0.15.0` are all unchanged.

Transcription server: 6/6 pytest tests pass across the Starlette 0.50 → 1.6 major version boundary.

TypeScript: 9/9 LiteLLM jest suites (77/77 individual tests) pass.

Prisma migration: `prisma db push` against an existing 1.85.1 schema succeeded with no drops and no `--accept-data-loss` needed. The schema grew from 64 to 70 base tables; `LiteLLM_DailyGatewayRequests` is the new table. The `db-init.ts` safety gate still correctly detects and rejects a contaminated database.

Proxy boot: the proxy starts in approximately 4 seconds, `GET /health/liveliness` returns 200, and the boot log reports `db: connected`.

Config acceptance: the proxy accepted all config keys without complaint — `enable_tag_filtering`, `store_prompts_in_spend_logs`, `allow_requests_on_db_unavailable`, and `callbacks: ["smtp_email"]`.

Model catalog: `GET /model/info` returned 43 entries, byte-identical to the baseline captured on 1.85.1. The parsed catalog produced 15 deduped entries, also byte-identical to baseline. Wildcard model names (`claude-opus-5*`) still arrive as literals from the proxy, confirming that `catalog.ts:96`'s trailing-`*` strip still applies and that wildcard expansion did not change shape.

Tenant isolation: the three-tenant tag-to-project mapping is identical after upgrade — tag routing still routes each tenant's requests to its own Vertex project.

Budget round-trip: `budget_reset_at` set via the `/tag/update` → `/budget/update` sequence survived correctly; the `litellm_budget_table` nesting in the response held as expected.

Usage envelope: `GET /tag/daily/activity` returned a `results[]` envelope intact.

### Required workaround

LiteLLM 1.97.0 cannot start against the version of FastAPI that its own declared metadata permits. It imports the private symbol `get_flat_dependant` from `fastapi.dependencies.utils` in `litellm/proxy/management_endpoints/management_v1/common.py:7`. That symbol was removed in FastAPI 0.140.7. LiteLLM's own metadata declares `fastapi>=0.136.3,<1.0`, which allows FastAPI 0.140.7 and above.

To work around this, `requirements.txt` carries `fastapi>=0.136.3,<0.140.7`, tightening the upper bound below the breaking FastAPI release. This constraint must be removed when LiteLLM ships its own ceiling on FastAPI — leaving it in place past that point risks blocking a future LiteLLM upgrade unnecessarily.

### Not verified

`/v1/rerank` response shape: not verified locally because `COHERE_API_KEY` is absent in the development environment. `resolve-reranker.ts:84` reads `results[].index` and `results[].relevance_score` with no fallback. This remains an open risk until the endpoint is exercised in a deployed environment with a live Cohere key.

`/tag/daily/activity` metrics nesting: only the outer `results[]` envelope was checked. The scratch database used for verification contained no spend rows, so the `breakdown.entities[tag].metrics` nesting that `usage-view.ts:108` reads was not exercised with real data. It will be confirmed naturally once the upgrade reaches a deployed environment with existing spend history.

### Pre-existing, not caused by this change

Four jest suites fail on `develop` independently of this work: `compact-session`, `email-inbound/intake`, `resolve-context-window`, and `convert-exulu-tools-to-ai-sdk-tools`. This branch touched zero `src/` files.

A `StarletteDeprecationWarning` about `httpx`/`httpx2` appears from `fastapi/testclient.py` during the transcription pytest run. This is test infrastructure only and does not affect production `server.py`.
