# WhatsApp channel for agents — Design

**Date:** 2026-11-16
**Status:** agreed with Daniel Claessen 2026-11-16; not yet planned or built
**Repos:** `exulu/backend` (channel config, webhook, linking, run), `exulu/frontend` (agent
editor section, link page)
**Related specs:** `2026-10-27-agent-guardrails-design.md` (should ship before a client
opens this channel to customers), `2026-10-27-rbac-retrieval-hardening-design.md`

## 1. Context & intent

Agents can be published to external users through guest access: the user opens
`/public/agents/<id>`, signs in, and chats in the browser. Newlift asked for the same agent
to be reachable over WhatsApp, because their customers' technicians stand in a lift shaft
with a phone, not a laptop.

This design adds **channels** to an agent: a configurable, per-agent connection to a
messaging platform. WhatsApp is the first and only channel type built here. The transport
is Vercel's Chat SDK (`chat` + `@chat-adapter/whatsapp`, MIT, 4.45.0 at the time of
writing), which runs inside our Express server and handles Meta's webhook handshake,
signature check, deduplication, formatting and message splitting.

WhatsApp has no login. The design therefore binds a WhatsApp sender to an existing IMP
account before the agent answers anything, through a flow modelled on CLI device logins:
the bot hands out a link, the user signs in on the web, receives a one-time code, and
sends that code to the bot. From then on the run happens **as that user**, so sessions,
RBAC, the external rate limit and guardrails apply without a second access model.

## 2. Goals, non-goals

**Goals**

- A WhatsApp number can be attached to an agent in the agent editor, by an admin, without
  a deployment. Credentials are stored encrypted and never returned by the API.
- No message from an unlinked sender reaches the model or costs anything beyond a fixed
  reply.
- A linked sender is an ordinary user of the agent: same permissions, same limits, same
  session history (WhatsApp conversations appear in their history rail on the web).
- Link lifetime is configurable per channel, default 7 days.
- Disabling the account, revoking the link, unpublishing the agent or disabling the channel
  takes effect on the next message.
- The channel abstraction is generic enough that a second platform is a new adapter and a
  new credential form, not a second design.

**Non-goals (v1)**

- Inbound media (photos, voice notes, documents). The bot answers with a fixed "text only"
  message. The adapter supports media; this is the obvious second step.
- Proactive messages and Meta templates. The bot only ever replies inside the 24-hour
  window that the customer's own message opens.
- Sources, citations, document previews, buttons, cards.
- Agents in guest mode `public` or `password`. Only `regular` (login) is supported; see §5.1.
- Streaming. WhatsApp cannot edit a message; the SDK buffers and sends once.
- Any other channel type.

## 3. Decisions taken (with Daniel, 2026-11-16)

| # | Decision |
|---|---|
| 1 | Channels are a product feature of the IMP, configured per agent. Entitlement key `channels`. |
| 2 | Transport is the Chat SDK, embedded in the backend. No separate service. |
| 3 | Access is by account linking with a one-time code, web → WhatsApp direction. |
| 4 | Link lifetime defaults to 7 days and is configurable per channel. |
| 5 | Runs execute as the linked user; there is no "WhatsApp guest" identity. |

Calls made while writing this, open to challenge:

- The lifetime is **fixed from the moment of linking**, not sliding. Predictable for the
  operator ("at most N days after a login"); a sliding window would let an active number
  stay linked indefinitely.
- Inbound runs go through BullMQ, so the channel requires the `queues` entitlement, the
  same dependency routine webhooks already have.
- A second message while a run is in flight gets a fixed "still working" reply and is not
  queued (§5.4).

## 4. Configuration

### 4.1 `agent_channels`

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | Also the webhook path segment. |
| `agent` | uuid | One channel of a given type per agent in v1 (unique on `agent`, `type`). |
| `type` | text | `"whatsapp"`. |
| `enabled` | boolean | Default false. |
| `config` | json | Non-secret settings, below. |
| `secrets` | text, hidden | AES-encrypted JSON (`encrypt`/`decrypt` from `auth/credential-store.ts`). Never exposed through GraphQL or REST, same treatment as `guest_password_hash`. |
| `verify_token` | text | Generated by us, shown once in the editor for pasting into Meta. |

`config` for WhatsApp:

```jsonc
{
  "phoneNumberId": "1234567890",     // Meta's ID, not the number
  "displayNumber": "+49 ...",        // for the wa.me link and the UI
  "linkTtlDays": 7,                  // 1–365
  "sessionIdleHours": 8,             // new session after this much silence
  "locale": "de",                    // language of the fixed replies: "de" | "en"
  "texts": {}                        // optional overrides of the fixed replies, by key
}
```

`secrets`: `{ "accessToken": "...", "appSecret": "..." }`. The access token must be a Meta
System User token; the token shown in Meta's API Setup page expires within a day and the
editor says so.

A channel can only be enabled when the agent has `guest_access = true` and
`guest_auth_mode = "regular"`. Changing either on an agent with an enabled channel
disables the channel and tells the admin why.

### 4.2 `channel_links`

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | |
| `channel` | uuid | |
| `identity` | text | The adapter's canonical user identifier (the last segment of the SDK thread ID). This is a phone number today and may be a Meta business-scoped user ID; never parse it. Unique on (`channel`, `identity`). |
| `user` | number | The IMP user. |
| `linked_at`, `expires_at` | timestamp | `expires_at = linked_at + linkTtlDays`, fixed at link time. |
| `revoked_at` | timestamp, nullable | |
| `last_seen_at` | timestamp | |

Re-linking an identity replaces its row. One user may link several identities.
Changing `linkTtlDays` affects new links only.

### 4.3 Link codes

Not a table. Redis key `channel-link:<sha256(code)>` → `{ channelId, userId }`, TTL 10
minutes, consumed with `GETDEL` so a code works exactly once. Format `XXXX-XXXX` from a
32-character alphabet without look-alikes (40 bits). Requesting a new code invalidates the
user's previous unconsumed code for that channel.

## 5. Runtime

### 5.1 Why only `regular` mode

Linking presupposes an account. A `public` agent has nothing to link to and would be open
to anyone who has the number, with no per-user limit to hold the cost; a `password` agent
would need the password typed into a chat that the phone keeps forever. Both are left out
until someone needs them.

### 5.2 Webhook

`GET` and `POST /webhooks/whatsapp/:channelId`, mounted with `express.raw` before the JSON
parsers (the signature is over the raw bytes; `/webhooks/routine` is the precedent).

1. Unknown or disabled channel → 404, no detail.
2. Missing `channels` or `queues` entitlement → 503.
3. Build a Web `Request` from the Express request and hand it to
   `bot.webhooks.whatsapp(request)` for that channel's `Chat` instance; write the returned
   `Response` back. The SDK answers Meta's `GET` challenge against `verify_token`, verifies
   `X-Hub-Signature-256` against `appSecret`, drops duplicates and ignores status-only
   deliveries.

`Chat` instances are created lazily per channel and cached in-process, keyed on the row's
`updatedAt`, because the SDK fixes its adapters at construction. State adapter is
`@chat-adapter/state-pg` on the existing database with its own key prefix. (The Redis
adapter depends on `redis ^5`; the backend is on `^4.7`.) Persistent state is required:
the adapter stores identity aliases there so a conversation survives Meta rotating a
user ID.

A global rate limit on the route mirrors `routineWebhookRateLimitExceeded`.

### 5.3 Message handling

One `onDirectMessage` handler per instance. It does no model work; it decides and returns.
In order:

1. **Not text** → fixed reply `textOnly`.
2. **Looks like a link code** (the whole message matches the code pattern, case and
   whitespace tolerant) → §5.5. Never forwarded to the model, linked or not.
3. **Command**: `/neu` or `/new` starts a new session; `/abmelden` or `/logout` revokes
   the link. Fixed confirmation.
4. **Resolve the link.** No row, expired, or revoked → fixed reply `linkRequired` with the
   link URL, at most once per identity per 10 minutes (Redis counter); otherwise silence.
5. **Re-check access on every message**: the user still exists and is active, and
   `evaluateGuestChatAccess(agent, user.id)` allows. Otherwise treat as unlinked and mark
   the link revoked.
6. `externalRateLimitExceeded(user.id)` → fixed reply `rateLimited`.
7. A run is already in flight for this identity (Redis lock) → fixed reply `stillWorking`.
8. Otherwise enqueue a `channel_message` job on a new `channel_inbound` queue with
   `{ channelId, threadId, identity, userId, messageId, text }`, mark the message read and
   start the typing indicator.

### 5.4 The run

The job runs where routine runs do. It:

1. Takes the per-identity lock (TTL above the run timeout).
2. Finds the session: the newest `agent_sessions` row for this user and agent whose
   `metadata.channel.id` matches and whose last message is younger than
   `sessionIdleHours`; otherwise creates one, titled with the first 50 characters of the
   message, `metadata.channel = { type, id, identity }`.
3. Calls `generateSync` with the agent, the linked user, the session and the message.
   The run is flagged as a guest turn, so everything keyed on `treatAsGuest` /
   `isPublicSurface` (hidden sources, external step cap, guardrail scope `external`)
   applies even though there is no HTTP request from a browser.
4. Posts the final text through the adapter as Markdown. The adapter converts formatting
   and splits at 4,096 characters.
5. On failure posts the fixed reply `runFailed` and records the error on the session.
6. Releases the lock.

WhatsApp's typing indicator lapses after about 25 seconds, so the job refreshes it while
the run is active.

`generateSync` is used rather than the stream because nothing can be shown early and
because it is the path the guardrails design finalises internally: with guardrails
enabled, the text this job posts has already passed the output check.

### 5.5 Linking

1. The `linkRequired` reply carries `<app>/public/agents/<agentId>/link/whatsapp`.
2. That page requires the normal guest login (existing `/auth` flow with a destination
   back to the page).
3. Signed in, the page calls `POST /public-agents/:id/channels/whatsapp/link-code`
   (authenticated; rejects when the channel is disabled or the user fails the guest gate)
   and shows the code together with a button
   `https://wa.me/<displayNumber>?text=<code>` and the same URL as a QR code for desktop.
   One tap opens WhatsApp with the code prefilled.
4. The user sends it. The handler hashes the message, `GETDEL`s the key, checks the
   channel matches, writes the `channel_links` row and replies `linked` with the expiry
   date.
5. A wrong or expired code gets `codeInvalid`. Five failed attempts per identity per hour,
   then silence for the rest of the hour.

The code is a bearer token for ten minutes: whoever sends it first is linked to the
account that requested it. Hence the short TTL, single use, the attempt limit, and the
page listing the user's linked numbers (masked, `+49 •••• 1234`) with an unlink button, so
an unexpected link is visible and removable.

### 5.6 Fixed replies

Keys: `linkRequired`, `linked`, `codeInvalid`, `textOnly`, `rateLimited`, `stillWorking`,
`runFailed`, `newSession`, `unlinked`. Shipped in German and English, selected by
`config.locale`, overridable per channel through `config.texts`. None of them is generated
by a model.

## 6. Frontend

- **Agent editor**: new section `sections/channels.tsx`, placed after guest access and
  disabled with an explanation unless guest access is on in `regular` mode. Fields: phone
  number ID, display number, access token and app secret (write-only; shown as "set"),
  link lifetime, session idle time, reply language. Shows the webhook URL and verify token
  to copy into Meta and the two webhook fields to subscribe (`messages`,
  `user_id_update`). A "Test connection" button calls the Graph API for the phone number
  and reports the result. Below it, the list of linked numbers (masked, user, linked,
  expires, last seen) with revoke.
- **Link page**: `app/public/agents/[id]/link/whatsapp/page.tsx`, in the guest shell,
  honouring `?lang=`. Code, wa.me button, QR code, countdown, linked numbers with unlink.
- Entitlement-gated like other enterprise sections.

## 7. Security and privacy notes

- Secrets are encrypted at rest and write-only in the API. The webhook path contains only
  the channel ID, which is not a secret; authenticity comes from Meta's signature.
- Unlinked senders can trigger at most one fixed reply per 10 minutes and no model call.
- `channel_links.identity` is personal data (a phone number). It is masked wherever it is
  displayed, included in the user data export, and deleted with the user.
- Link, unlink, revoke, failed-code lockout and rejected-access events go to the audit log
  when the audit layer is on.
- A channel widens the audience of an externally published agent. Instructions in the
  prompt remain a soft control; the guardrails design is the hard one and should be live
  on an agent before its channel is opened to customers.
- Conversation content and phone numbers pass through Meta. The operator has to cover
  that in its privacy notice and processing agreements; the editor section says so.

## 8. Operator prerequisites (Meta side)

Verified Meta Business account; a WhatsApp Business Account; a phone number not registered
in the WhatsApp app; a Meta app with the WhatsApp product; a System User with a permanent
token; the webhook URL and verify token from the editor entered in the app, subscribed to
`messages` and `user_id_update`. Typically several days of lead time, independent of our
build.

## 9. Costs

Meta does not charge for free-form replies inside the customer-opened 24-hour window, and
this design sends nothing else. Per-turn model cost equals a web guest turn. No judge or
classifier is added by the channel itself.

## 10. Testing

- Webhook: unknown channel 404; bad signature rejected; challenge answered; duplicate
  delivery processed once; status-only delivery ignored.
- Handler order of §5.3, one test per branch, asserting **no job is enqueued** for
  non-text, code-shaped, unlinked, expired, revoked, disabled-user, unpublished-agent,
  rate-limited and in-flight cases.
- Linking: code single-use; expired code; code for another channel; attempt lockout;
  `expires_at` computed from the channel's lifetime at link time; re-link replaces.
- Run: session reuse inside the idle window, new session after it and after `/neu`; run
  flagged as guest turn; failure posts `runFailed`; lock released on failure.
- API: `secrets` and `verify_token` absent from every GraphQL and REST projection.
- Enabling rules of §4.1, including auto-disable when guest mode changes.

## 11. Left to the builder

- Posting from the worker: confirm the SDK lets a second `Chat` instance (same config,
  same state) post to a thread ID outside a webhook handler, or call the adapter's
  `postMessage` directly.
- How `@chat-adapter/state-pg` creates its tables, and whether that fits our schema
  bootstrap.
- The exact way to mark a queued run as a guest turn without a browser request
  (synthetic header versus an explicit `generateSync` option; the guardrails spec's
  `isGuardedCaller` must see it either way).
- Which user field means "active"; this spec only requires that a disabled account fails
  step 5 of §5.3.
- Typing-indicator refresh interval against current Meta behaviour.

## 12. Open questions

1. Meta's Business API terms restrict general-purpose AI assistants and allow
   business-specific support bots. An agent answering about the operator's own products
   should qualify; each operator confirms this against the current terms before go-live.
2. `external-rate-limit.ts` is in-process. With the handler in the server and nothing
   else counting, that holds; if the check ever moves into the worker it needs Redis.
3. Worker runs call the server's LiteLLM. A bulk ingestion run would slow WhatsApp answers
   the way it slows the web app today.

## 13. Deferred

Inbound media; proactive templates (for example "your link expires tomorrow"); plain-text
source lists; `public` and `password` agents; further channel types (Teams, Telegram) on
the same tables.
