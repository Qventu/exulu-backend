### Why Stage 1 cannot reach 95 % as specified

1. `usedMemoryIds` does not mean "memories the answer used". The spec's marker
   (`chunk_id: "memory:<item_id>"`) matches **zero** rows in `exulu-test`
   (`agent_messages.content::text ~ 'memory:[0-9a-f-]{36}'` → 0). Every subset case is therefore built by the
   extractor's fallback regex, which collects **every `newton_memory_context` chunk the old knowledge-search
   tool returned** — the superseded retriever's topK-10 candidate list. A hit demands set-equality with that
   list, so the gate measures "does the new retriever return the same ten rows as the old one", not recall.
2. Two cases are arithmetically impossible at limit 10: `a59f0eab` carries 11 ids, `27f4de9a` carries 12.
3. **Three of the 26 distinct ids no longer exist** in `newton_memory_context_items`
   (`a00a377e…`, `5d521862…`, `92c62ea9…`). They are cited by exactly those two cases, so both are
   impossible at *any* limit. The ceiling is 10/12 = 83.3 % < 95 %.
4. Qualitatively the new recall looks better, not worse. For the Ziehl-Abegg inverter question the new set
   contains "Regler Error 532 … Ziehl-abbeg frequency inverter", "CBM2 Bremsenbetrieb mit 24V"; the old
   candidate list for the same question contains "Softstarter = Liftstarter Synonym" and
   "FST Türparameter Max — Zyklen".
