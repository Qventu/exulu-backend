# LiteLLM 1.97.0 Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the pinned LiteLLM proxy from 1.85.1 to 1.97.0 and prove locally that the four integration surfaces (model catalog, tag budgets, usage analytics, inference passthrough) still behave identically.

**Architecture:** LiteLLM is not a library we import — it is a Python process the backend spawns and supervises (`src/exulu/litellm/supervisor.ts:168`). The upgrade is a one-line pin change in `ee/python/requirements.txt`. All the work is verification, because the venv is shared with our ML stack and our own FastAPI transcription server, and because the proxy's HTTP response shapes are an untyped contract our parsers depend on.

**Tech Stack:** Python 3.12 venv (`ee/python/.venv`), pip, Prisma (Python client 0.15.0), TypeScript/Jest, pytest, PostgreSQL.

**Spec:** `docs/superpowers/specs/2026-08-19-litellm-1.97-upgrade-design.md`

## Global Constraints

- **Repo/branch:** `/Users/daniel.claessen/Desktop/Projects/exulu/backend` on `chore/litellm-1.97`. Verify both in the same command as any commit.
- **Target version:** `litellm[proxy]==1.97.0` exactly. Not a range.
- **Pins that must NOT move:** `prisma==0.15.0`, `google-cloud-aiplatform>=1.38`, `torch==2.5.1`, `torchaudio==2.5.1`, `torchvision==0.20.1`, `transformers>=4.48,<5`, `huggingface_hub<1.0`, `whisperx>=3.4.0`. If pip proposes changing any of these, **stop** — the resolve was verified to leave them untouched, so a change means something is wrong.
- **Scope is bump-and-verify.** No TypeScript source changes, no adoption of new LiteLLM features, no `expose_router_debug_in_errors` change. If verification proves a TS change is needed, stop and report rather than expanding scope silently.

A 1.97.0 `prisma db push` adds columns (`dcr_bridge`, `oauth2_flow`, `LiteLLM_DailyGatewayRequests`) and rolling the pin back does **not** roll the schema back.
