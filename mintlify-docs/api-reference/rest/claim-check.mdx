---
title: "Claim Check API"
description: "Verify an answer's claims against a set of sources and get a grounding verdict per sentence and per claim."
---

`POST /claims/check` extracts the checkable claims from an answer and verifies each one against the sources the caller provides. It does **not** fact-check against the open web, a search engine, or any knowledge the model itself holds — the caller's `sources` array is the only evidence the check ever sees. This makes the endpoint usable by any client, including ones that never touch an IMP knowledge base: post an answer and the documents it should be grounded in, and get back a verdict.

The request payload is trusted as given — the backend checks the answer against exactly the sources it was handed, nothing more and nothing less.

## How it works

The answer is split into sentences. Each sentence is checked for verifiable content and disambiguated in context, then decomposed into one or more atomic claims. Each claim is verified against the supplied sources and gets a verdict. The response reports both a per-sentence breakdown (so a UI can highlight the original answer) and a per-claim breakdown (so a UI can show evidence and rationale).

Sentences that carry nothing to verify — introductions, conclusions, opinions, sentences too ambiguous to resolve — are **not treated as failures**. They are reported as not checked, with a reason, and excluded from the score's denominator entirely. An answer made only of such sentences reports `score.label: "n/a"`, never a 0% score, which would misread as total failure.

## Request

```jsonc
{
  "question": "…",                       // required
  "answer": "…",                         // required
  "sources": [ { "id": "s1", "name": "handbuch.pdf", "content": "…" } ], // optional, defaults to []
  "agent": "uuid",                       // optional: agent config, model, and second-chance retrieval
  "session": "uuid", "messageId": "…",   // optional, provenance only
  "model": "…",                          // optional, super-admin callers only
  "locale": "de",                        // optional, auto-detected from the answer if omitted
  "options": {
    "fidelity": "fast",                  // "fast" (default) or "paper"
    "completions": 1,
    "reRetrieve": true,
    "thresholds": { "warn": 0.1, "alert": 0.3 },
    "caps": { "maxSentences": 120, "maxClaims": 200, "maxReRetrievals": 10 }
  }
}
```

| Field | Type | Description |
|---|---|---|
| `question` | `string` | The question the answer responds to. Required, non-empty. |
| `answer` | `string` | The answer text to check, as originally produced (markdown as streamed). Required, non-empty. |
| `sources` | `{ id: string, name?: string, content: string }[]` | The caller's evidence. `id` must be unique within the request and is echoed back in `claims[].evidence[].sourceId`, so a caller can map evidence back to its own records. **Optional** — an omitted `sources` key validates as an empty array (the schema's permissive shape is deliberate), not a validation error. With no evidence to verify against, every claim the engine extracts comes back `unsupported` with "no evidence was available for this claim"; pass sources if you want anything to resolve as `supported` or `contradicted`. |
| `agent` | `string` | Optional agent UUID. When set, the caller's API key must be scoped to it and the caller must have read access; the agent's `claim_check` configuration and second-chance retrieval become available. |
| `session`, `messageId` | `string` | Optional provenance fields; not used for access control. |
| `model` | `string` | Optional model override. **Accepted only from a super-admin caller** — see Model resolution below. A non-admin caller who sets this field gets `403`, not a silently-ignored parameter. |
| `locale` | `string` | Optional. Defaults to a locale detected from the answer text. |
| `options` | object | Optional per-call overrides. Omitted keys fall back to the agent's `claim_check` configuration, then to the engine defaults (`fidelity: "fast"`, `completions: 1`, `reRetrieve: true`, `thresholds: { warn: 0.1, alert: 0.3 }`, `caps: { maxSentences: 120, maxClaims: 200, maxReRetrievals: 10 }`). |

### Model resolution

The model to run the check with is resolved in order, first hit wins:

1. the request's `model` — **only honoured when the authenticated caller is a super admin**. Model resolution performs no per-user model entitlement check of its own, so a non-admin caller naming a model here would otherwise be able to reach any model configured on the deployment, including the most expensive one available, on an endpoint deliberately fed arbitrary text. A non-admin caller who sets `model` gets `403` instead, naming the alternative;
2. `claim_check.model` configured on the named `agent`;
3. that agent's `utility_model`;
4. the agent's own model;
5. the platform's default claim-check model, for agent-less calls.

If none of these resolves to a usable model, the endpoint responds `400` naming `claim_check.default_model` as the missing configuration, rather than silently picking a model nobody chose. Everyone other than a super admin who wants a non-default model should configure `claim_check.model` on the agent (step 2) rather than requesting it per call.

## Response

```jsonc
{
  "status": "ok",                        // or "partial" — see below
  "score": {
    "claims": 60, "supported": 51, "contradicted": 2, "unsupported": 7,
    "unsupportedShare": 0.15, "label": "warn"
  },
  "sentences": [
    { "index": 0, "start": 0, "end": 118,
      "state": "checked", "claimIds": ["c1"] },
    { "index": 1, "start": 119, "end": 150,
      "state": "no_verifiable_content", "reason": "…", "claimIds": [] }
  ],
  "claims": [
    { "id": "c1", "sentenceIndex": 0, "text": "Die FST-2XT arbeitet mit 230 Volt.",
      "inferred": false, "verdict": "contradicted",
      "evidence": [ { "sourceId": "s1", "quote": "…" } ],
      "rationale": "…", "rechecked": false }
  ],
  "usage": { "calls": 18, "inputTokens": 114203, "outputTokens": 24880 },
  "timings": { "splitMs": 12, "selectDisambiguateMs": 2140, "decomposeMs": 1980,
               "evidenceMs": 60, "verifyMs": 3310, "totalMs": 7502 },
  "limits": { "truncated": false, "sentencesSkipped": 0 },
  "notes": []
}
```

`sentences[].start`/`end` are character offsets into the exact `answer` string the caller sent — `answer.slice(start, end)` reproduces the sentence verbatim, which a UI can use to highlight the original text.

### `status`

`"ok"` or `"partial"`. The engine never throws for an in-progress check — a provider failure, a hit cap, or any other recoverable problem degrades the result to `"partial"` rather than failing the request. **A `partial` result is still a `200`**: it is a legitimate, documented outcome, not an error. Check `notes` for what was degraded and why.

### Sentence states

| State | Meaning |
|---|---|
| `checked` | The sentence produced at least one claim that was verified. |
| `no_verifiable_content` | The sentence carries nothing to check (an introduction, a conclusion, an opinion) or its decomposition found no claim. |
| `cannot_disambiguate` | The sentence is too ambiguous in context to resolve into a checkable claim. |
| `not_checked` | The sentence was not evaluated — a cap was hit (`reason: "cap_exceeded"`), or a stage call failed for it. |

Sentences without verifiable content are reported as **not checked**, never as failures: they are excluded from `score`'s denominator and surfaced with a `reason`, not counted against the answer.

### Verdict vocabulary

Each claim gets exactly one of three verdicts:

| Verdict | Meaning |
|---|---|
| `supported` | The sources confirm the claim. |
| `contradicted` | The sources say otherwise — this is the hallucination signal. |
| `unsupported` | The sources don't cover this claim at all — a coverage gap, not a contradiction. |

`contradicted` and `unsupported` are reported as separate counts deliberately: "the sources disagree with the answer" and "the sources are silent on this" are different problems with different fixes. The score's `unsupportedShare` is `(contradicted + unsupported) / claims`, which drives `score.label` against `options.thresholds` (`ok` below `warn`, `warn` up to `alert`, `alert` at or above). An answer with no checkable claims at all reports `score.label: "n/a"`.

When `agent` is set and `options.reRetrieve` is on, `unsupported` claims get one additional targeted retrieval each (capped by `options.caps.maxReRetrievals`) and may flip to `supported` with `rechecked: true` — the evidence existed in the knowledge base, the answer just wasn't shown it. Callers who bring their own `sources` without an `agent` do not get this second pass; their `sources` array is the only evidence that is ever consulted.

## Status codes

| Status | When |
|---|---|
| `200` | The check ran, `status` is `"ok"` or `"partial"`. |
| `400` | The request body failed validation, or no model could be resolved (`detail` names `claim_check.default_model`). |
| `401` | Authentication failed. |
| `403` | The API key is not scoped to the named `agent`, or the caller cannot read it. Also returned when a non-super-admin caller sets `model` in the request body. |
| `404` | The deployment is not licensed for claim check. The endpoint does not advertise a feature the deployment has not bought, so this looks identical to a route that does not exist. Also returned, with `{ "detail": "Agent {id} not found." }`, when an `agent` is named that does not exist. |
| `413` | A payload cap was exceeded (see below). The engine is never invoked. |
| `429` | The caller's rate-limit budget, or the server's global in-flight budget, is exhausted. |
| `500` | The engine failed in a way it could not degrade past (this should be rare — see `status: "partial"` above for the normal degradation path). |

## Payload caps and rate limits

One request can cost on the order of 18 LLM calls over arbitrary caller-supplied text, so these limits are load-bearing, not cosmetic — they apply to every caller and every role, including internal ones.

**Payload caps** (`413` when exceeded, before anything is sent to the engine):

| Limit | Value |
|---|---|
| Answer length | 200,000 characters |
| Number of sources | 200 |
| Total source content | 2,000,000 characters, summed across all `sources[].content` |

**Rate limits** (`429` when exceeded):

| Limit | Default | Scope |
|---|---|---|
| Per-user, per minute | 30 | Every authenticated identity, every role — not just external/guest users. |
| Per-user, per hour | 300 | Same scope as above. |
| Global in-flight | 20 concurrent checks | Process-wide, so a burst from one caller cannot drain the provider quota the rest of the deployment (including chat) needs. |

The in-flight slot is always released once a check finishes, whether it succeeds, returns `partial`, or the engine throws — so a failure never leaks the global budget.

## Example

```bash
curl -X POST "https://your-imp-host/claims/check" \
  -H "Authorization: Bearer $EXULU_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "question": "Womit arbeitet die FST-2XT?",
    "answer": "Die FST-2XT arbeitet mit 230 Volt. Das ist beeindruckend.",
    "sources": [{ "id": "s1", "name": "handbuch.pdf", "content": "Die FST-2XT arbeitet mit 230 Volt." }]
  }'
```

This call has no `agent`, so the model comes from the platform's default claim-check model. To use an `agent` with its own `claim_check.model` configuration instead, add `"agent": "<uuid>"`. Only a super-admin key may add `"model": "<model-id>"` to pick a model per call; any other caller gets `403` for that field.

For this input, the first sentence resolves to a `supported` claim and the second — an opinion with nothing to verify — is reported as `no_verifiable_content`, so `score.label` is `"ok"`.
