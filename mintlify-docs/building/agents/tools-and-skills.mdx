## Tools vs. skills

IMP distinguishes two kinds of agent capability:

- **Tools** are server-side integrations — API calls, search functions, code runners, and data connectors — installed and managed by administrators. Each tool has a type, a category, and optionally a set of parameters that must be bound before the agent can use it.
- **Skills** are reusable prompt-level capabilities: pre-written reasoning patterns, formatting rules, or multi-step response strategies. Skills are toggled on per agent and do not require parameter configuration.

## The Tools & skills section

The section shows only what the agent has: three groups — **Sub-agents**,
**Skills** and **Tools** — each with a count, the enabled entries, and an
**Add …** button. A tool row keeps its configure and info buttons; the switch
or the remove button takes it off the agent. A group without entries shows
what the button would add.

## Enabling a tool

Click **Add tools** (or **Add sub-agents**, **Add skills**). The picker lists
the instance's catalogue: search by name, description or category, narrow
tools by category with the chips, tick what you want, and confirm with
**Add N**. Entries the agent already has are shown ticked and cannot be added
twice. When exactly one added tool needs configuration, its configuration
sheet opens right away; otherwise the rows carry a "needs configuration"
badge until you fill them in.

## Per-tool configuration

Many tools expose one or more parameters that must be bound to a value before the agent can call them. Parameter types include:

- **string** — a plain text value.
- **number** — a numeric value.
- **boolean** — `true` or `false`. The configuration sheet renders a toggle; the stored value is the string `"true"` or `"false"`, parsed to a native boolean at runtime.
- **json** — a structured object. When the stored value is already an object it passes through as-is; when it is a string, it is JSON-parsed at runtime. Use this for complex configuration like the KB editor's `knowledge_bases` map.
- **variable reference** — a dropdown that lets you pick a named variable from the organization's Variables store instead of hard-coding a value. Using variable references keeps secrets out of the agent form and allows administrators to rotate values in one place.

To configure a tool:

<Steps>
  <Step title="Enable the tool">
    Toggle the tool on in the Tools & skills section. If the tool has parameters, the configuration sheet opens automatically.
  </Step>
  <Step title="Fill in each parameter">
    For each parameter, either type a literal value or select a variable reference from the dropdown. The parameter's description tells you what the tool expects.
  </Step>
  <Step title="Close the sheet">
    Close the sheet. The configuration is staged locally until you save the agent.
  </Step>
  <Step title="Save the agent">
    Click **Save** in the workbench header or Save Bar.
  </Step>
</Steps>

You can reopen the configuration sheet at any time by clicking the **Configure** button (gear icon) on an already-enabled tool row.

## Knowledge base editor

The **Knowledge base editor** is a built-in tool in the **default** category. Enabling it lets the agent create and update items in selected knowledge bases during chat, including attaching documents from the session files to file fields — and read what it may write.

When you enable the tool, IMP opens a custom configuration sheet instead of the standard parameter form. The sheet lists every knowledge context in the deployment; check a context to grant the agent write access to it. For each checked context, two switches appear:

- **Create** — the agent may add new items to this context.
- **Update** — the agent may modify existing items in this context.

A context with both switches off grants no access even though it appears checked. Only contexts you explicitly include and permit are writable.

At the bottom of the sheet, the **Skip approval** toggle controls whether the agent prompts the user for confirmation before writing. When off (the default), the user sees an approval prompt for every create or update call; when on, writes proceed immediately.

<Note>
Created and updated items still respect the [tool approvals](/user-guide/chat/tool-approvals) setting on the conversation. Skip approval only suppresses the per-call confirmation built into the KB editor — if the user has disabled tool approvals globally, that setting takes precedence in the other direction.
</Note>

### The four generated tools

At runtime the entry expands into concrete tools per selected knowledge base, named after the context's id:

| Tool | What it does |
| --- | --- |
| `create_<context>_item` | Creates one item from the fields passed; the context's required fields are mandatory. Needs **Create**. |
| `update_<context>_item` | Changes an existing item, found by its `id` or `external_id`; only the fields passed change, the others keep their values. Needs **Update**. |
| `get_<context>_item` | Reads one item by its `id` or `external_id` and returns its fields as JSON. |
| `find_<context>_items` | Returns the items matching a structured filter, as a JSON array. |

A knowledge base the agent may write is a knowledge base it may read: the two read tools arrive with the first write switch, have no configuration of their own, and — unlike the write tools — **never ask for approval**, because they change nothing. Skip approval does not apply to them. Before they existed, an agent could only read an item back by calling update with a patch that changed nothing, which asked the user to approve a write for a read.

Both read tools take an optional **`fields`** array that narrows the output to the fields it names — `id` always comes back, whether you name it or not. Omitted, `get` returns everything readable on the item, and `find` returns `id`, `updatedAt`, `name`, `description`, `tags`, `external_id` and the context's own non-file fields; `createdAt`, `rights_mode` and `archived` come back from `find` only when asked for by name. `find` also takes **`limit`**: 20 by default, 50 at most — a larger number is clamped, not refused. Neither tool ever exposes a `hidden` field: not in the output, not in `fields`, not as a filter.

#### Filtering with `find`

`where` maps a field name to one object of operators, and several fields are combined with AND. Six operators are available:

| Operator | Matches |
| --- | --- |
| `eq`, `ne` | equal to / not equal to the value |
| `in` | any value from a list |
| `contains` | a substring for text and enum fields, containment for `json` — not available on number, boolean, date or uuid fields |
| `gte`, `lte` | at least / at most — numbers and dates (`lte` with `0` also matches items where the field is empty) |

```json
{
  "where": {
    "archived": { "eq": false },
    "status": { "in": ["active", "in review"] },
    "updatedAt": { "gte": "2026-01-01" },
    "metadata": { "contains": { "kunde": { "land": "CH" } } }
  },
  "limit": 10
}
```

The last filter reaches inside a `json` field: the value is a fragment of the stored object, matched by containment. Where that field declares a schema, the path is checked against it — `metadata.kunde.land` has to be a path the schema defines, or the call comes back naming the paths that do exist, instead of an empty result that reads like "there are none". An unknown field name or an unsupported operator is refused the same way, with the valid names listed; nothing is silently ignored.

<Note>
The timestamp fields are `createdAt` and `updatedAt`. `find` is an exact, field-by-field lookup and returns its matches in no particular order — for a meaning-based search across item content, use the agent's knowledge retrieval instead.
</Note>

### KB editor safety model

The KB editor enforces multiple independent gates before any write reaches the database:

1. **Explicit per-context opt-in** — a context is writable only if the agent's configuration sheet explicitly enables it with at least one of Create or Update.
2. **Row-level write access** — for update calls, the platform checks whether the active user has write access to that specific item (matching the item's `rights_mode` — public, private, users, roles, or teams). Items the user cannot write are silently reported as not found to avoid probing.
3. **Guest refusal** — write tools require an authenticated user. Anonymous guest sessions receive a hard refusal; no DB call is made.
4. **Schema exclusions** — the following are never exposed in the tool schema: `uuid` (reference fields), `calculated` fields, fields marked `editable: false`, and `hidden` fields. Reserved internal parameter names are also excluded.
5. **Files only from the session** — a `file` field takes the name of a file from the conversation's session files. The platform checks the field's allowed types, copies the object into the user's own upload storage (the same shape the upload dialog produces), and stores that key; the knowledge base's processor and embeddings then run as they do for an upload from the UI. The agent cannot attach a file by URL or by path.

The read tools pass through the same opt-in and the same guest refusal, and every item they touch is checked against the user's **read** rights — see [Knowledge base write access](/building/agents/access-and-safety#knowledge-base-write-access).

## Skill author

The **Skill author** is a built-in tool in the **default** category. Enabling
it lets the agent turn a procedure the user just completed into a skill in the
instance's library, or publish a new version of a skill the user may write.
The agent gets four tools: `skill_list` and `skill_read` (what exists),
`skill_create` and `skill_update`. Its configuration has three switches:
**Create**, **Update**, and **Skip approval**.

A system-prompt block comes with the tool. It tells the agent to offer a skill
only after complex, multi-step work that is likely to recur — typically work
that produced files, documents, code or a structured analysis, or a
multi-step retrieval the user runs regularly — and never for a single question
against a knowledge base or a one-off correction, which belongs in memory.

Creating or updating a skill shows a card in the chat, like a memory
proposal: the user can change the name and the description, sees the files
the agent proposes, chooses who may use the skill (private, public, or a
scope of users, roles or teams), and — when they may edit the current agent —
ticks **Enable it on this agent**. Nothing is written before they confirm.
After a successful create or update the card offers **Reload skills**, which
re-installs the agent's skills into the live sandbox so the new version is
usable in the same conversation; otherwise it loads with the next turn.

<Note>
An update always publishes a new version: unchanged files carry over, the
files in the proposal replace or add, and listed paths are removed. Earlier
versions stay available on the skill's page.
</Note>

## Sub-agents as tools

When **sub-agent orchestration** is enabled on this deployment, other agents appear in the Tools & skills section under the **Agents** category. Enabling an agent-as-tool means the current agent can call the sub-agent during a conversation — for example, routing specialized questions to a domain expert agent.

A toggle at the top of the Agents category controls whether the current agent's own tools and sub-agents are shown in the list ("Show this agent's tools & sub-agents"). Self-referential loops are excluded automatically.

<Tip>
Use sub-agents to decompose complex workflows: a general assistant can delegate to a coding agent, a data agent, or a support agent depending on what the user asks.
</Tip>

## Skills

Below the tools accordion, the **Skills** section lists available skills. Each skill row shows the skill name and description with a toggle. Skills have no parameters — enabling one activates it for all conversations this agent handles.

<Warning>
Skills run inside the file sandbox. Enabling a skill on an agent that has the **File sandbox** toggle off has no effect — the skill scripts cannot execute because no sandbox is provisioned. Turn on the File sandbox toggle in the [Chat experience](/building/agents/workbench#chat-experience) section before enabling skills.
</Warning>

See [Skills](/building/skills/overview) in the Building section for how to define custom skills.
