## Access control

An agent's **Access** section in the [workbench](/building/agents/workbench) determines which users can open the agent in Chat. The RBAC control presents four mutually exclusive sharing modes.

### Sharing modes

| Mode | Who can chat with the agent |
| --- | --- |
| **Private** | Only you — the agent is hidden from everyone else's Chat picker. Good for agents under active development. |
| **Users** | Specific users you select from the directory. The panel shows a user search; add as many as you need. A summary line reads "Shared with `{n}` users." |
| **Roles** | All users who hold a specific role. The panel shows a role picker. A summary reads "Shared with `{n}` roles." |
| **Public** | Every signed-in user in the organization sees the agent. |

<Info>
Team-scoped sharing ("Teams" mode) is available when your deployment has the RBAC teams feature enabled. Until that flag is active, the mode list shows only Private, Users, Roles, and Public.
</Info>

### Changing access

<Steps>
  <Step title="Open the Access section">
    In the workbench, scroll to or click **Access** in the section navigation.
  </Step>
  <Step title="Select a mode">
    Choose Private, Users, Roles, or Public.
  </Step>
  <Step title="Add users or roles">
    If you chose Users, search and add each user. If you chose Roles, pick one or more roles. Public and Private require no further selection.
  </Step>
  <Step title="Save">
    Click **Save** in the workbench header. The new sharing rules take effect immediately.
  </Step>
</Steps>

### How access interacts with admin settings

Administrators can also apply organization-wide defaults and override access controls from the Administration area. An agent set to Public still respects any global budget or model restrictions the administrator has configured.

## Guest publishing

Internal sharing modes cover authenticated IMP users. To expose an agent to visitors outside your organization — without requiring an IMP account — enable **Guest access** in the [workbench](/building/agents/workbench#guest-access).

When guest access is on, the agent is reachable at a public URL (`/public/agents/{id}`). Three authentication modes are available: **Public** (no credentials required), **Password** (shared password gate), and **Login** (external email self-registration with persistent sessions).

<Note>
Guest access supersedes the legacy `rights_mode=public` field. If an agent has both guest access enabled and the legacy public flag, the guest-access gate — with its chosen authentication mode and abuse limits — applies, and the old anonymous path is bypassed. Agents that have never had guest access set keep their previous behavior unchanged.
</Note>

For the full configuration guide, see [Guest access](/building/agents/guest-access).

## Knowledge base write access

When the [Knowledge base editor](/building/agents/tools-and-skills#knowledge-base-editor) tool is enabled, an agent can create and update knowledge context items during chat — and read the items of the same contexts. The following safety model applies:

- **Explicit per-context opt-in** — only contexts checked in the tool's configuration sheet, with at least one of Create or Update enabled, are writable. All other contexts are read-only regardless of the agent's knowledge settings.
- **Dual gate** — a write attempt must pass both the agent-level configuration (is the context opted in?) and a row-level write check (does the active user have write access to that specific item?). Either gate failing blocks the write.
- **Guest refusal** — write tools require an authenticated user session. Requests from anonymous guest sessions are refused before any database call is made.
- **Schema exclusions** — the following are never included in the tool schema: `file` and `uuid` fields, `calculated` fields, fields marked `editable: false`, `hidden` fields, and reserved internal parameter names. This limits what the model can write to well-defined, safe columns.

Reading is part of the same grant — a context the agent may write is a context it may read — and it obeys the item's own rights:

- **Row-level read access** — every item a read tool returns is checked against the active user's read rights for that specific item (its `rights_mode` — public, private, users, roles, or teams). An item the user may not read is reported as not found, in the same words as an item that does not exist, and nothing of it is shown: no field value, no name, not even the fact that the id exists. `find` lists only the items the user may read.
- **Guest refusal** — the read tools need an authenticated user session too. An anonymous guest session gets the not-found answer, and an empty list from `find`, before any database call is made.
- **Hidden fields stay hidden from the agent's tools** — no agent tool, read or write, exposes a field marked `hidden`: it appears in no read output, cannot be requested by name, and cannot be filtered on. (That is a guarantee of the generated tools, not a platform-wide one — see the field's own documentation for where it does and does not apply.)
- **No approval, because nothing changes** — the read tools never prompt for confirmation. That is a deliberate asymmetry with the write tools, and it costs nothing in safety: the gates above decide what the user may see, and reading leaves no trace in the knowledge base.
