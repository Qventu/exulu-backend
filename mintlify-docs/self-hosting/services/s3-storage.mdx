IMP uses S3-compatible object storage for chat attachments, session files, and knowledge source uploads. The bucket must exist before the application starts — IMP does not create it.

## Supported backends

- **AWS S3** — set `COMPANION_S3_ENDPOINT` to empty / omit it.
- **MinIO** — set `COMPANION_S3_ENDPOINT` to the MinIO API URL (e.g. `http://exulu-minio:9000`) and IMP enables `forcePathStyle: true` automatically.
- Any other S3-compatible store that supports presigned PUT URLs.

## Presigned URL flow

File uploads go directly from the browser to the object store via presigned PUT URLs. The backend generates a signed URL, returns it to the frontend, and the browser uploads the file directly without passing through the backend. This keeps large uploads off the API process.

<Warning>
**AWS SDK checksum gotcha.** AWS SDK for JavaScript v3.729 and later injects an `x-amz-checksum-crc32` header (computed over an empty body) into presigned PUT URLs by default. MinIO and some other S3-compatible stores validate that checksum against the uploaded bytes and reject the PUT with a checksum mismatch error, causing session file uploads to silently fail.

IMP disables this default by setting `requestChecksumCalculation: "WHEN_REQUIRED"` and `responseChecksumValidation: "WHEN_REQUIRED"` on the shared S3 client (fix shipped in backend commit `fa88d2e`). If you build `@exulu/backend` from a revision older than that commit, upgrades to AWS SDK >= 3.729 will break file uploads against MinIO.
</Warning>

## Create the bucket before starting IMP

IMP does not create the bucket. Create it first:

```bash
# MinIO via mcli
mc alias set local http://localhost:9000 <root-user> <root-password>
mc mb local/<bucket-name>
```

Or create it through the MinIO web console at `http://localhost:9001`.

## Configuration reference

| Variable | Example | Description |
|---|---|---|
| `COMPANION_S3_REGION` | `eu-central-1` | Bucket region. For MinIO this matches the region you configured. |
| `COMPANION_S3_KEY` | — | Access key ID |
| `COMPANION_S3_SECRET` | — | Secret access key |
| `COMPANION_S3_BUCKET` | `exulu-uploads` | Bucket name. Must exist before startup. |
| `COMPANION_S3_ENDPOINT` | `http://exulu-minio:9000` | Endpoint URL. Omit for AWS S3. Set to the MinIO API URL for MinIO. |

## Compose excerpt (MinIO)

```yaml
exulu-minio:
  image: quay.io/minio/minio:RELEASE.2025-04-22T22-12-26Z
  restart: unless-stopped
  command: server /data --console-address ":9001"
  environment:
    MINIO_ROOT_USER: "${MINIO_ROOT_USER}"
    MINIO_ROOT_PASSWORD: "${MINIO_ROOT_PASSWORD}"
  ports:
    - "9000:9000"   # API
    - "9001:9001"   # Web console
  volumes:
    - minio-data:/data
  healthcheck:
    test: ["CMD", "mc", "ready", "local"]
    interval: 30s
    timeout: 20s
    retries: 3
```

Point the backend at MinIO:

```ini
COMPANION_S3_ENDPOINT=http://exulu-minio:9000
COMPANION_S3_REGION=eu-central-1
COMPANION_S3_KEY=<your-access-key>
COMPANION_S3_SECRET=<your-secret-key>
COMPANION_S3_BUCKET=<your-bucket-name>
```

## Operational notes

**Network reachability.** `COMPANION_S3_ENDPOINT` is used server-side (by the backend) to generate presigned URLs. The endpoint must be reachable from the backend container. If the backend and MinIO are on the same Docker network, use the container name (e.g. `http://exulu-minio:9000`). The presigned URL returned to the browser must resolve from the end user's machine — configure a public URL or reverse proxy for MinIO's API port if users are outside the Docker network.

**Bucket policy.** The bucket does not need to be public. Presigned URLs grant time-limited read and write access to individual objects without a bucket-level public policy.

**Signature expiry.** IMP presigns URLs with a 1-day expiry (`expiresIn = 86400`). Uploads or downloads attempted after the signature expires will receive a 403 from S3.

## Reading cache

When the agent reads a PDF or Office document with `parse_document`, the extracted text is stored in the same bucket and reused by every later read of the same content on this instance. Reading a scanned or long document costs OCR and vision calls, so this is done once per document and not once per chat.

**On by default.** The store is on for every deployment with file uploads configured (`COMPANION_S3_BUCKET`), also without `attachments.documentProcessor`: plain text-layer reads (`pdftotext`, `officeparser`) are stored too. Only `EXULU_DOCUMENT_CACHE_DAYS=0` switches it off.

**Bucket permissions.** The S3 credentials of the backend need list and delete rights on the `derived/` prefix in addition to read and write: the daily sweep lists and deletes expired objects there. Without them the store still works, but expired text is never removed and each sweep logs an error.

**Where it lives.** Under a `derived/` prefix at the top of the bucket (after `COMPANION_S3_PREFIX`, if set):

| Key | Content |
|---|---|
| `derived/content/<sha256>/<id>.md` | The extracted text. `<sha256>` is the hash of the file's bytes, `<id>` identifies the reading configuration. |
| `derived/pointers/<hash>.json` | A small record per file (`etag`, `lastModified`, `size` and `sha256`, all taken from the download that was hashed) so a repeat read does not have to download the file to hash it. The record is trusted only while the file's current ETag, last-modified time and size all match it; a record in the older two-field shape is ignored. |

Do not delete, expose or point other tools at `derived/` by mistake: it is created and managed by IMP. No file list, project page, prompt listing or sandbox shows it, the browser upload policy cannot write to it, and the generic `/s3/*` routes refuse it. It is not served by any route. The agent's read tools return its text only after they have resolved a file the caller can read, so text is given only to someone who holds a file with the same content. The one thing it reveals indirectly is that someone on the instance read the same document before: the read is immediate and the progress card says **already read**.

**What the key contains.** The text is stored per content and per reading configuration: the engine, the OCR model name and the vision model of `attachments.documentProcessor`, or `pdftotext` / `officeparser` when no processor is configured. Changing the engine, the OCR model or the vision model therefore makes every document be read once more on its next use. For a processor the file extension (`.doc` and `.docx` take different paths) and `processor.maxPagesPerChunk` are part of the key too. Model names are the aliases from your LiteLLM config, and the alias is what is stored in the key: remapping an alias to a different underlying model does not invalidate stored text. Rename the alias, or delete `derived/`, to force a re-read. Concurrency settings are not part of the key. A replaced file has different content and so a different entry. The page count is kept in the object's metadata (`exulu-pages`), so a stored read reports it without parsing the text.

**What is not stored.** Refusals and failures (too many pages, scan without a processor, unreadable text layer, processor error), results that fell back to the text layer when a processor is configured, and results where the vision pass failed for some pages. The next read tries again.

**Expiry.** `EXULU_DOCUMENT_CACHE_DAYS` (default `365`) is how long text is kept, counted from when it was written. An older entry is treated as absent and read again. Every server replica runs the sweep (about a minute after start and then once a day; workers do not), so with several replicas the sweep runs several times a day, which is harmless. It lists `derived/` one page at a time and deletes expired text and pointer objects. With `0` the store is off and the next sweep deletes everything under `derived/`.

<Warning>
Deleting a file, a session or a project does not delete the stored text of its content: other files may have the same content, so the text stays until it expires or the sweep removes it. For data-protection requests, set `EXULU_DOCUMENT_CACHE_DAYS=0` (the next daily sweep empties the store), or delete the objects under `derived/` in the bucket by hand. Erasure therefore needs one of the two: without them, stored text stays for up to `EXULU_DOCUMENT_CACHE_DAYS` days. Deleting them is safe: nothing else depends on them, and documents are simply read again when they are next used.
</Warning>

**Long first reads.** With a document processor configured, `parse_document` reads PDFs up to `EXULU_DOCUMENT_MAX_PAGES` pages (default `300`), in OCR chunks run in parallel (`attachments.documentProcessor.ocr.concurrency`, default 3, 1 to 8). Reads by the agent (`parse_document` and files attached to a message) share a ceiling of 8 OCR and 8 vision calls at once across all users in the process; more wait in a queue. The ceiling applies to chat reads only: knowledge-base processing is unchanged and keeps its own per-document settings. When reading in chat, a single OCR call is stopped after 180 seconds and a single vision call after 120 seconds (knowledge-base processing is unchanged and has no such limit); a call that runs out of time counts as a failed attempt and is retried like any other. The first read of a long document takes minutes. It keeps running and stores its result even if the user leaves the conversation. Lowering `EXULU_DOCUMENT_MAX_PAGES` does not refuse a document that is already stored: a stored text is served as it is. The 50-page limit `EXULU_ATTACHMENT_MAX_PAGES` still applies to files attached directly to a chat message. If two users read the same uncached document at once on different backend replicas, both extract it and the later write wins. See [Environment variables](/self-hosting/environment-variables#document-reading) and [Configuration](/developers/core/exulu-app/configuration#attachments).
