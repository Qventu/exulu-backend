Release · 2026-05-29

What's new in Exulu.

Five shipped: a workspace inside every chat, smart follow-ups, a configurable model gateway, single-zip skill uploads, and GDPR endpoints for super-admins.

Session files panel

Every chat now has its own workspace.

A new folder icon in the chat header opens a 340-pixel sidebar listing every file the session has touched — what the agent wrote, what you uploaded, what got mirrored from a bash artifact. Click any row to preview text, code, markdown, images, PDFs, and (via a LibreOffice-backed cache) Office documents.

Files dropped into the upload zone are signed straight to S3 at the same prefix the agent's writeFile and bash-artifact mirroring already use, then synced into the live sandbox so the agent's next turn can readFile them without a restart. The panel polls every five seconds; cross-tab edits show up within the same window.

The panel is explicit about scope: a persistent notice at the top reminds you that session files don't cross into other sessions, projects, or knowledge bases.

Follow-up suggestions

Never stare at a blank input again.

Opt in per agent: when suggestions_enabled is on, the chat fires a stateless POST /agents/suggestions/:agentId after each assistant reply and renders up to three short follow-up prompts above the textarea. Click one to populate the input — you press send yourself.

The route uses the agent's own model via generateObject with a fixed Zod schema ({ suggestions: string[] }), so JSON shape is enforced at the provider level. Tokens count toward the same per-agent rate limit and statistics the main run uses; a new submit aborts any in-flight suggestion call. If anything fails — rate limit, schema mismatch, network — the row silently doesn't appear.

LiteLLM proxy integration

Bring your own model gateway.

Set EXULU_USE_LITELLM=true and Exulu boots LiteLLM as a supervised sidecar from the existing ee/python/.venv. The resolveModel() seam introduced in the previous release gains a single branch: in LiteLLM mode it bypasses the DB models table entirely and constructs a language model via @ai-sdk/openai-compatible against the proxy, with modelId used directly as the LiteLLM model_name.

The Models admin page becomes a read-only viewer over LiteLLM's /model/info endpoint. The agent and chat model pickers source from the same catalog. Rate limits, token budgets, cost tracking, and cross-provider routing all move into LiteLLM's config.yaml — one file, every provider.

Enable
EXULU_USE_LITELLM=true
LITELLM_MASTER_KEY=sk-…
LITELLM_CONFIG_PATH=ee/python/.litellm/config.yaml  # default
Catalog (config.yaml)
general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY

model_list:
  - model_name: vertex-flash
    litellm_params:
      model: vertex_ai/gemini-2.5-flash
      vertex_project: os.environ/GOOGLE_VERTEX_PROJECT
  - model_name: claude-haiku
    litellm_params:
      model: anthropic/claude-haiku-4-5
      api_key: os.environ/ANTHROPIC_API_KEY

Skill bundle upload

Drop a .zip, get a skill.

The New Skill modal grows a mode toggle: Create blank (unchanged) or Create from upload. In upload mode, drag a .zip or a single SKILL.md onto the dropzone, name it, click Create.

Behind the scenes: a presigned PUT lands the file in a per-user staging key, then the backend unpacks the archive into skills/<skillId>/v1/... — the same prefix the per-file editor writes to. Anthropic-style zips with a top-level wrapper folder get stripped automatically. Path traversal, missing SKILL.md, archives over 50 MB, and bundles with more than 500 entries are rejected with explicit error messages before any S3 write happens.

On success, you land directly in the skill editor with every file already wired up.

GDPR export & delete

Article 15 and Article 17, in two HTTP calls.

Two super-admin routes, root-mounted, no new dependencies. GET /users/:id/data-export streams a ZIP with the user's account row (sensitive auth material stripped), all sessions with their messages inlined, feedback, prompt favorites, tracking events, and a README that names DSGVO Art. 15 explicitly.

DELETE /users/:id hard-erases the same footprint inside a single Postgres transaction (agent messages, sessions, feedback, prompt favorites, tracking, RBAC entries, the user row itself), then sweeps the user_<id>/ S3 prefix best-effort. Self-delete by a super-admin is blocked. Deletion is final — no soft-delete, no recovery window.

Export — DSGVO Art. 15
curl -H "Authorization: Bearer $TOKEN" \
     https://api.exulu.com/users/42/data-export \
     -o user-42-export.zip
Delete — DSGVO Art. 17
curl -X DELETE \
     -H "Authorization: Bearer $TOKEN" \
     https://api.exulu.com/users/42
