Release · July 8, 2026

A platform roundup, eleven upgrades deep.

No single marquee this time — a stack of improvements that landed together across the whole platform. Replies you can listen to, memory that asks before it writes, RBAC-safe reads for retrieval builders, one consent per OAuth provider, a live model catalog, and API keys safe enough to ship in a browser. From the chat surface all the way down to your GCP invoice — plus seven smaller fixes at the bottom.

Chat experience

Read replies aloud

Any assistant message becomes audio — one click on the speaker.

Every completed assistant message now carries a speaker button in its actions row. Click it and the reply is cleaned up for listening — markdown stripped, code blocks skipped — synthesized to MP3, and played right there in the chat. Click again to pause; click a different message to switch. Replays are instant: each message keeps its audio cached, so a second listen never touches the backend.

Long replies don't make you wait, either. The message is split into sentence-sized chunks and synthesized with up to five requests in flight, so the first audio starts in roughly two to three seconds even on a multi-page answer.

The same endpoint is open to any authenticated client — text in, MP3 out. It's live on deployments running LiteLLM with a TTS model and voice configured (EXULU_USE_LITELLM=true, TTS_MODEL, TTS_VOICE), with a 4,000-character input cap per call.

REST — text in, MP3 out
# Any authenticated client can synthesize speech:
curl -X POST "$EXULU_BACKEND/speech" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{"text":"Here is the summary you asked for."}' \
  --output reply.mp3

Memory that asks first

No memory is saved until you choose private or public.

When an agent wants to remember something, it now has to ask you first: private (visible only to you) or public (shared with the team). If the agent tries to save without that answer, nothing is written — the tool refuses and sends the agent back to ask. Your choice isn't a cosmetic label: it maps straight onto the record's rights mode, the same RBAC field that governs every other record in Exulu.

Recall quality got a quiet overhaul in the same pass. Structured memory fields are validated and normalized at write time, so a near-miss value gets fixed or dropped instead of persisting as un-recallable garbage. Every memory also captures the surrounding conversation context — so when it's retrieved months later, the agent knows why it exists — and memory types are persisted whenever the memory context defines one.

Agent runtime

File sandbox, per agent

File tools only for the agents that need them.

Sandbox file tools — readFile, writeFile, bash — are now opt-in per agent. A single switch in the agent editor's Chat experience section decides whether the agent gets a sandbox at all. Knowledge-only agents stay lean: no shell, no file tools, and no more spurious shell calls from an agent that only ever needed to answer questions.

The chat composer follows the setting live. When the sandbox is off, the Session files entry in the ＋ menu is disabled with the reason spelled out inline — so users are never left wondering where their upload button went. Flip the switch on for agents that run skills or generate files, and everything lights back up.

Skill sandbox artifacts persist to S3

Sandboxes are disposable. The files your agents make aren't anymore.

Sandboxes are ephemeral by design — which used to mean a process restart or sandbox teardown between turns silently ate every report, script, and dataset an agent had produced. Resume the session, and the agent's work was gone.

Now every artifact an agent writes is mirrored to S3 as it's written, scoped per user and session. On a cold start, previously written artifacts are restored into the session directory before the agent runs, so it picks up exactly where it left off — and local files always win over stale restores, so un-synced work is never overwritten. Skill source files are excluded; only artifacts persist. And it's fail-soft everywhere: missing S3 config or a failed upload never fails the tool call, because the local write already succeeded.

The bonus: writeFile now returns a presigned S3 URL alongside the local path. A generated report is a shareable link the moment it exists.

writeFile now answers with a shareable URL
{
  "success": true,
  "path": "sessions/3f2a.../quarterly-report.md",
  "url": "https://s3.eu-central-1.amazonaws.com/…/user_42/sessions/3f2a…/quarterly-report.md?X-Amz-Signature=…",
  "key": "uploads/user_42/sessions/3f2a.../quarterly-report.md"
}

Sandbox output truncation: overflow-proof tool results

cat a 60-page PDF without killing the context.

One oversized tool result used to be fatal. An agent that read a huge file or ran a log-spewing script got the output back verbatim — enough to overflow the context window and take the whole turn down with it, unrecoverably.

Sandbox tool output is now capped at 25% of the agent's context window (128k tokens by default, so a 128,000-character cap per call). Oversized output keeps its head and tail, and the omitted middle is replaced by a marker that tells the agent exactly what happened — plus the surgical commands to fetch any specific section. The split matches where the signal lives: file reads keep 95% head (files are read top-to-bottom), while stderr keeps a 40% tail, because errors live at the end.

What the agent sees instead of a context overflow
[READFILE OUTPUT TRUNCATED: output was 412830 characters; showing first
121600 and last 6400 characters (limit: 128000 = 25% of 128000-token
context). 284830 characters omitted. To read specific sections use:
  grep -n "pattern" <file>        # find specific text
  sed -n '1,50p' <file>           # lines 1–50
  head -n 100 <file>              # first 100 lines
  tail -n 100 <file>              # last 100 lines
  awk 'NR>=10 && NR<=50' <file>   # lines 10–50]

Developer platform

ExuluReadApi: RBAC-safe reads for retrieval clients

Build retrieval on authorized rows — not on raw tables.

Custom retrieval pipelines need reads that context.search() can't express — "give me chunks 0–20 of this exact file", "does this context have an entity layer?" — and until now the answer was hand-rolled SQL against raw tables, one refactor away from silently skipping access control.

That surface is now supported SDK, one import away. authorizedRead reads chunks for known items with the RBAC clause applied inside the SQL query, so a user can never receive a chunk from an item they aren't allowed to see — and it refuses unconstrained reads outright, so an accidental table scan is impossible. embedQuery embeds a query with the same embedder the context indexes with, and entitiesAvailable probes whether a context's entity layer actually exists before you wire tools against it. ExuluContext.getItems became RBAC-aware in the same pass. And for code that must go lower, the table-name resolvers (getTableName, getChunksTableName) are exposed on the same surface, so per-context tables are resolved instead of hand-assembled.

This isn't speculative API design: it's the exact surface the agentic retrieval pipeline announced yesterday runs on. Supported surface, not internals.

From the SDK
import { ExuluReadApi } from "@exulu/backend";

// RBAC-safe chunk read for a known file — access control applied in SQL.
const chunks = await ExuluReadApi.authorizedRead(context, user, roleId, {
  externalIds: ["handbook.pdf"],
  chunkIndexRange: { from: 0, to: 20 },
});

// Embed with the context's own embedder, resolved per caller.
const vector = await ExuluReadApi.embedQuery(context, "notice period");

// Probe the entity layer before wiring entity tools.
const hasEntities = await ExuluReadApi.entitiesAvailable(context);

OAuth: one consent per provider

Connect Google once — every Google tool is signed in.

Per-tool OAuth consent made multi-tool integrations feel broken: six jira_* tools meant clicking Connect six times against the same OAuth app, with the same scopes. Tokens were keyed per tool, so every tool had to earn its own.

Tokens are now keyed per (provider, user). A tool opts in by declaring provider: "jira" on its OAuth config, and every tool sharing that provider shares one token per user — one consent screen, then everything works. Sharing is kept sane at construction time: tools claiming the same provider must agree on client credentials, endpoints, and the identical scope set, or registration throws with a precise error. No silent scope escalation, ever.

It's opt-in and non-breaking. Omit provider and tokens stay per-tool exactly as before; the originating tool id stays on every token row for audit.

From the SDK — ExuluOauthConfig
new ExuluTool({
  id: "jira_create_issue",
  // ...
  oauth: {
    provider: "jira", // ← share one consent across every jira_* tool
    authorizationUrl: "https://auth.atlassian.com/authorize",
    tokenUrl: "https://auth.atlassian.com/oauth/token",
    clientId: process.env.JIRA_CLIENT_ID!,
    clientSecret: process.env.JIRA_CLIENT_SECRET!,
    scopes: JIRA_SCOPES, // must match across the provider — enforced at boot
  },
});

Models: agents decoupled from providers

One model catalog. Every agent, every route, one resolver.

Agents used to hard-wire a provider and an API key — and the code that turned that pair into a language model was copy-pasted across eight call sites. Both are gone. Model configuration now lives in one place, the LiteLLM proxy's config.yaml, and every consumer — chat routes, the OpenAI-compatible gateway, MCP, evals, tools — resolves "agent → model" through a single resolver with RBAC in the loop.

The /models page renders that source of truth as a read-only catalog of everything the proxy serves: context windows, modalities (Vision / PDF / Audio / Tools), input and output cost per million tokens, active status, and tags — searchable, with a per-model detail sheet. What admins configure and what agents can use can no longer drift apart.

Traceability comes with it: the model used is persisted on every assistant message, so "which model wrote this?" is a query, not an archaeology project. And the x-exulu-model-override header swaps the language model for a single request — the chat model selector rides on exactly this.

GraphQL — the catalog the UI renders
query GetLiteLLMCatalog {
  litellmCatalog {
    model_name
    active
    type
    max_input_tokens
    max_output_tokens
    supports_vision
    supports_function_calling
    input_cost_per_million_tokens
    output_cost_per_million_tokens
  }
}

Cost & governance

Spend, fully accounted

The gap tagged totals miss, now on the card.

Exulu's dashboards count user-attributed LLM requests — so the platform's totals always ran at or below what LiteLLM saw globally, and the difference was invisible. Health checks, background jobs, untagged calls: real spend, no explanation.

Now, whenever that unattributed gap exceeds 1% of the unfiltered total, a quiet second caption appears on the Spend and Tokens cards on Home and across the analytics KPI strip: "+ $12.34 unattributed". Trivial and negative gaps stay hidden, and the hint only renders once both queries have resolved — no flash of wrong numbers while the dashboard loads. Your cards now add up to your bill.

Vertex billing labels

Your GCP invoice now knows which agent spent what.

Vertex spend used to arrive in Google Cloud Billing as one undifferentiated line. Internal analytics could slice usage per user and agent — but the invoice itself couldn't, and finance works from the invoice.

Every Vertex generateContent call now carries up to six Google Cloud billing labels — provider, user, role, project, and agent — sanitized to GCP's rules and visible in Cloud Billing reports (with Google's usual ~24-hour lag). The injection is deliberately paranoid: any failure forwards the original request unmodified, so a billing label can never break a model call. And only opaque IDs leave the box — no emails, no names. Pair it with the in-product LiteLLM tagging: that one is for your dashboards, this one is for the bill.

Injected into every Vertex generateContent call

  "contents": [ "..." ],
  "labels": {

    "provider_name": "gemini-2-5-flash",
    "user_id": "42",
    "role_id": "f3a91c",

  }
}

API-key agent scoping (enterprise)

Mint a key that can talk to one agent — and nothing else.

Any key you ship client-side is a leaked key, eventually. Until now, that was an unacceptable risk: an API key could reach every agent and every mutation on the platform, so embedding an agent in a public page meant either a proxy layer or crossed fingers.

API keys now declare a scope mode. admin keeps today's broad behavior — every existing key migrates there with zero change. agents carries a whitelist of agent IDs and can call only the run route for those agents: no GraphQL mutations, no other agents, no admin surface. Enforcement is two-layered — an early scope check rejects out-of-scope requests at the route, and the record-access layer's blanket API bypass is now narrowed to admin-mode keys. A leaked scoped key can talk to exactly the agents it was minted for.

Spend stays controlled too: usage and budget caps are enforced in the LiteLLM proxy layer, so scoped keys inherit them automatically.

GraphQL — minting a scoped key
mutation CreateUser(
  $type: String, $apikey: String,
  $scope_mode: String, $agent_ids: JSON
) {
  usersCreateOne(input: {
    type: $type, apikey: $apikey,
    scope_mode: $scope_mode,  # "admin" | "agents"
    agent_ids: $agent_ids     # whitelist when scope_mode = "agents"
  }) {
    item { id }
  }
}

Also shipped

Small fixes that make the whole platform feel tighter.

  • Stale tool approvals auto-decline. Move on to a new message and pending approval prompts resolve themselves — no zombie "Awaiting Approval" chips.
  • Chat text is WCAG AA. Response text now uses the theme foreground token — full contrast in both themes.
  • Smoother streaming on heavy turns. Multi-file agent turns no longer saturate the browser main thread while streaming.
  • Big PDFs OCR reliably. 60-page scans are split into ≤25-page chunks and processed in parallel — no more Vertex page-limit failures.
  • x-api-key accepted. API callers can authenticate with the industry-standard header alongside exulu-api-key.
  • Faster vector search. HNSW search tuned on every connection, and query embeddings computed once and reused across retrieval phases.
  • Redis fails fast. If Redis is unreachable at startup the server says so loudly and exits, instead of hanging half-alive.
