Release · Agent Evals

Ship agents you can trust.

Evals are now a first-class surface in Exulu: build named test suites, run any agent against them, compare every run side by side with red-amber-green scoring, and trace each score back to the transcript, the tokens, and the per-metric judge that produced it.

Results matrix

Every run, every case, side by side.

Open an eval set and every run becomes a lane in a single cases × runs matrix. The test cases run down a sticky left column; each run is a self-contained lane with its name, date, agent, a pinned Average row, and one cell per case. Completed scores render to one decimal, colored against that run's pass threshold — green at or above it, amber within twenty points below, red under that — so a whole suite's health reads at a glance.

The matrix is alive. Cells flip from a spinning Running to a colored score as the queue lands each result, and the lane Average updates and recolors with every landing — no reload. The runs and cases lists poll every ten seconds (the queue chip every five), so new runs and row changes appear on their own. In-flight cells show their real status — Waiting, Running, Failed, Delayed — a case outside a run's selection is a striped dash, and a lane with nothing finished says "No results yet" instead of a NaN average.

The matrix shows the last 3 runs by default, sorted oldest to newest so the freshest lane sits at the right edge; a quiet "Show older runs" rail reveals five more at a time. Each lane's overflow menu carries "Refresh results" for everyone, and "Start run", "Copy run", "Edit run" and "Delete run" for writers — starting confirms first, and completed score cells are now real keyboard-focusable buttons (they used to be inert divs).

GraphQL — every cell is a queue job — start runs from the API and watch the matrix fill:
mutation RunEval($id: ID!, $test_case_ids: [ID!]) {
  runEval(id: $id, test_case_ids: $test_case_ids) {
    jobs
    count
  }
}

Eval run wizard

Test your agents like you test your code.

One dialog configures an eval run in three sections. Essentials sets the run name, agent, and a test-case multi-select where every case shows a "N msgs" badge for its scripted conversation length, with a live "x of y" counter and one-click Select all. Eval functions is the same multi-select pattern — and checking a function that declares config reveals its settings inline: for the built-in LLM as Judge, a Configuration block with a prompt textarea for the judge instructions, scored 0–100 with {actual_output} and {expected_output} template slots.

Advanced stays out of the way in a collapsed section whose trigger summarizes it at a glance — "Advanced — Average · pass ≥ 70 · 300s" — covering scoring method (Average / Median / Sum), pass threshold, and timeout. Sensible defaults mean most runs never open it. Submit stays disabled until a name, an agent, at least one test case, and at least one eval function are set.

It's one modal doing three jobs: the same dialog powers create ("New run config"), edit ("Edit run config"), and copy — the table's Copy action re-opens it pre-filled as "name (Copy)" with a cleared id. And a run config is a plain API object, so you can script it directly.

GraphQL — a run config is just data — script it via GraphQL:
mutation CreateEvalRun($data: eval_runInput!) {
  eval_runsCreateOne(input: $data) {
    item {
      id
      name
      agent_id
      eval_functions
      scoring_method
      pass_threshold
    }
  }
}

Result deep-dive

Every score, explained.

Every completed cell in the matrix is now a door, not just a number. Click a finished score and a "Test result details" sheet slides in from the right with four tabs. Overview leads with the score, a duration card, a "Completed" status badge and the job ID, and a "Token usage" card splitting total tokens into input and output — a bare number turned into score, tokens, transcript, and per-function breakdown.

Messages replays the eval conversation in the same renderer the chat page uses, so you audit exactly what the agent said rather than a paraphrase. Functions breaks the composite score apart — one card per eval function with its name, id, individual score to two decimals, and the exact config it ran with. Raw is the full result metadata as pretty JSON for when you want everything. When a result carries an error, the Overview tab adds a destructive-bordered "Error details" card, so the same flow doubles as the debugging view.

The sheet only opens on real, finished data: in-flight and failed states render as status labels and are never clickable, so you can't deep-dive into a half-finished result. Completed cells are proper focusable buttons, so the whole sheet is keyboard-reachable.

Conversation test cases

Test cases that talk like your users.

Test cases are authored as real conversations, not one-line prompts. The Create test case modal has two tabs: Basic info for the name, description and required expected output, and Conversation to script a multi-turn exchange. Type a user message and press Enter to add it (Shift+Enter for a new line), or click Add message — "Add user messages in order. The agent will respond between each message automatically."

Every user turn you add gets a ghost assistant turn appended after it — "💬 Placeholder, generated agent response will be added here when the test case is run…" — display-only scaffolding that the agent's real reply replaces at run time. The transcript is the product's actual chat renderer, so user bubbles sit on the right with per-message edit and remove actions; removing a user message also removes its placeholder. You can attach up to ten files per message through the shared file picker (images, PDF, Office docs, CSV, audio, video), with an amber note reminding you the agent under test must support the attached media types.

The same modal opens pre-filled to edit existing cases and saves through the test-case mutations — and because the scripted conversation is stored verbatim in the record's inputs field, you can script cases programmatically.

GraphQL — test cases are plain records — script the conversation via GraphQL:
mutation CreateTestCase($data: test_caseInput!) {
  test_casesCreateOne(input: $data) {
    item {
      id
      name
      inputs
      expected_output
    }
  }
}

Every eval set, one searchable home

Eval suites get a permanent address, not a scattered set of fixtures.

The new /evals area gives eval suites a permanent address: a paginated table of eval sets — "Test agents against expected behavior and track scores across runs." — with a "Filter by name…" search box that filters server-side as you type, and a "Test case library" shortcut in the toolbar. Creating a suite is one dialog: "New eval set" opens "Create eval set" — "Create a new evaluation set. You can add test cases after creation." — with just a name and description, so the empty state is two fields away from gone.

Access is RBAC-gated on the evals right, the same predicate that drives the sidebar nav, so nav and page never disagree. Anyone without at least evals: read lands on a lock screen — "Access denied. You don't have permission to access Evals. Contact your administrator to request access." — and deleting a set is confirm-guarded and permanent.

A test-case library that outlives any one suite

Cases are named, versioned records — authoring and suite assembly stay separate steps.

Test cases now live in their own library at /evals/cases — "Create and manage test cases for evaluating agent performance." — where every case is a named, multi-turn conversation with an expected output, not a throwaway fixture buried inside a suite. Each row shows a Messages badge ("3 messages") that counts only the user turns you authored, so the auto-generated assistant placeholders between them never inflate the number.

From any eval set you pull cases in via "Add existing test cases" — "Pick from unassigned test cases. A case can belong to only one set." — so authoring and suite assembly are two separate, deliberate steps. Sets cap at "{count}/500 cases", and the case editor is the same two-tab modal you use everywhere: Basic info and Conversation, with a required expected output that can be an exact response or a description of what the output should contain.

The run queue, one quiet chip away

Runs execute on a background queue — its whole state fits in one chip, with a full console behind it.

Eval runs execute on a background queue, and its whole state now fits in one quiet chip above the results matrix — "Queue: 4 active · 1 failed" — polling every five seconds, turning the failed count red, and disappearing entirely when the queue is empty. Click it and a full console slides in ("Queue: eval_runs"): status tabs (Active / Waiting / Failed / Completed) with live counts, a jobs table with click-to-copy IDs, attempts and timestamps, and bulk actions — "Retry 3 job(s)", "Delete 3 job(s)", with an optional "Delete the original jobs after retrying" cascade.

Queue-level controls — "Pause queue", "Resume queue", "Drain queue" — are all confirm-guarded and, like every mutating action in the panel, visible only to users with evals: write; readers can still open and inspect everything. And the operation the Retry button fires is the same one that fans a run out into queue jobs — pass test_case_ids to re-run just the cases that failed.

GraphQL — one mutation fans a run out into queue jobs — the same call the console's Retry button makes:
mutation RunEval($id: ID!, $test_case_ids: [ID!]) {
  runEval(id: $id, test_case_ids: $test_case_ids) {
    jobs
    count
  }
}

A guardrail, not a dead end

No background workers? The evals area says so — and stays fully browsable.

If the deployment has no background workers, the evals area says so instead of failing silently: an orange banner — "Background workers are not configured" — explains exactly what still works: "Eval sets are viewable but runs can't execute. Configure Redis to enable evaluation runs."

It's deliberately a warning, not an error, because browsing and authoring stay fully functional — and only super-admins, the people who can actually fix it, get the "Configuration →" link.
