Release · Analytics

Know where every dollar goes.

Cost and usage analytics you can actually act on: a ranked spend leaderboard by agent, team, user or project; a daily trend you can read at a glance; and a URL-driven lens so any cost view is one link away.

Spend leaderboard

Who is burning the budget? Now you can see.

The Breakdown card splits the active measure — spend, by default — by a page-level dimension picker. A single "Split by:" Select in the page header re-scopes the whole card across Agents, Users, Projects, Teams, Roles and Routines. Because it lives in the header, next to the range picker, the scope is reachable at a glance regardless of which card has focus. Switch Agents to Teams and the leaderboard below re-ranks — new names, new magnitudes, new bars — and the description crossfades from "Agents · by spend" to "Teams · by spend".

The leaderboard is the successor to the legacy Leaderboard: a top-10 <ol> where each row keys off a stable id (no display-name collisions), draws a proportional purple bar with the bg-primary/10 token — width is value / topValue, so rank 1 is always full width — and marks the top three by rank numeral plus a subtle medal tint. Color is never the only carrier of meaning; the numeral is. Values are measure-aware: spend renders as USD currency ($1,204.50), tokens and requests as plain locale numbers, and the unit label under each value follows the measure.

A header toggle flips the same top-10 slice between two views — List, the leaderboard, and Share, a recharts donut on the --chart-1..10 ramp with a color-keyed legend so slice identity is never hover-only. LiteLLM tags carry only stable ids, so the top-10 ids are hydrated to human names via six *_BY_IDS GraphQL queries — Postgres is the source of truth for names, and an unresolved id falls back to the raw id string.

GraphQL — Tag ids carry no names — the leaderboard hydrates them from Postgres on switch:
query GetTeamsByIds {
  teamsPagination(page: 1, limit: 200) {
    items {
      id
      name
    }
  }
}

Trend chart

Every dollar, every day, at a glance.

One card, titled "Trend", plots the selected measure per day across the lens window — a monotone recharts AreaChart whose live description, "Daily {measure} across the selected range.", names the active measure so the y-axis flip is never silent. The measure control is a single segmented Tabs — Spend (USD currency), Tokens (prompt + completion), Requests (successful) — the only in-region scope control after the legacy LensType Select retired.

The switch never refetches. LiteLLM's daily rows carry spend, prompt_tokens/completion_tokens and successful_requests explicitly, so selecting a measure is a field projection over the already-loaded window — the area re-draws instantly to the new series with no network round-trip. The y-axis unit follows the measure automatically, currency for Spend and plain locale counts for Tokens and Requests, and measure is URL-backed (?measure=tokens): the URL is the single source of truth, so a switch is deep-linkable and drives both the trend card and the breakdown card beside it in one router.replace.

The card owns its own states through ChartCard: a layout-mirroring skeleton while the first window loads, an inline error with a Retry button ("We couldn't load this chart."), and a quiet empty state ("No activity in this window") when the window has zero total. Motion respects prefers-reduced-motion — under reduce, the area swaps with no tween.

Date-range lens

Bookmark the exact cost view. Send it to anyone.

The whole analytics view is URL-driven, so any view is a shareable link. The range row is a segmented Tabs [24h · 7d · 14d · 30d] (default 14d), and a custom window is entered from the date-pill's calendar. Picking any two dates flips the lens to a custom range and drops the active preset; the popover closes and the whole page — KPIs, Trend, Breakdown — recomputes off that one window via resolveWindow.

The lens is the URL. lensToSearchParams serializes the window into sorted query params — router.replace writes it without scrolling and useSearchParams reads it back, so there's no local state to drift. Copy the URL and the exact window travels with it: the date range, the measure, the dimension and the breakdown view are all part of the lens, so a shared link reproduces not just the date window but the full analytical framing.

A custom range is capped at 30 days (MAX_RANGE_DAYS). Picking an end more than 30 days past the start is blocked with the toast "Date range too large" / "Please select a date range of 30 days or less.", and days beyond the cap are disabled in the calendar. A deep-linked ?range=custom that exceeds 30 days is reset on load to the last 14 days with a one-shot toast. Legacy ?type=AGENT_RUN-style URLs still resolve — remapped to the equivalent dimension with a quiet "Filter updated" toast — and the URL canonicalizes on the next replace.

Every breakdown, one spreadsheet away

Export exactly the slice on screen as an entity-by-day pivot.

The Breakdown card's "Export CSV" button (aria label "Export the current breakdown as a CSV file") downloads exactly the slice on screen as an entity-by-day pivot: the top 10 entities as rows, one zero-filled column per day in the window, and a trailing Total — so the header reads Entity, 2026-07-01, 2026-07-02, …, Total. Empty days are present and zero-filled, not skipped.

Row labels are the hydrated human names, not the raw LiteLLM tag ids; spend cells keep six decimals while token and request cells stay integers, and the file is written with a leading UTF-8 BOM so Excel opens UTF-8 cleanly. The download is named analytics-{dimension}-{measure}-{start}-{end}.csv — e.g. analytics-agents-spend-2026-06-25-2026-07-09.csv — and the button is disabled while data is loading or when there are zero rows.

See the split, not just the ranking

The same top-10 slice, either as a leaderboard or a proportional ring.

The Breakdown card carries a two-button toggle in its header — a ranked "List" (aria "List view") and a "Share" donut (aria "Share view") — so the same top-10 slice reads either as an ordered leaderboard or as a proportional ring. The Share view draws a recharts donut plus a color-keyed legend below it, where each row shows the entity name, its value, and its share of the total as a whole-number percent (· {pct}%); slices under 5% drop their inline label to stay legible.

Spend is formatted as USD currency and token/request measures as plain locale numbers, and the ring honors prefers-reduced-motion by dropping the slice tween. The view choice writes lens.view, so it too is a URL param — the whole slice on screen, list or share, reflects the current lens.

LiteLLM tags carry ids; you see names

Every breakdown row is reconciled against Postgres names before you ever see it.

Analytics is 100% LiteLLM-driven, and LiteLLM tags carry only stable ids — so every breakdown row arrives as agent_id_…, user_id_…, and the like, and the frontend reconciles those ids against Postgres names before you ever see them. The card takes the top-10 ids for the active dimension and fires the matching by-ids GraphQL query — one per dimension, six in total — then maps each id to a human label. A user falls back name → "firstname lastname" → email → id, so a row is never a bare id if a name exists.

Both the ranked list and the CSV export read from that same hydrated map, so the names you see on screen are the names in the file. Alongside all of this, the Spend / Tokens / Requests KPI strip announced this morning now sits above a fully hydrated, exportable breakdown.

GraphQL — the literal id→name reconciliation the card fires for the active dimension:
query GetUsersByIds($ids: [ID!]!) {
  userByIds(ids: $ids) {
    id
    name
    firstname
    lastname
    email
  }
}
