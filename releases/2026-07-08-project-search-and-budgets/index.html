Release · July 8, 2026 · Agentic Retrieval, part 2

Projects in the pipeline. Budgets, decoupled.

Part 2 of the July 7 Agentic Retrieval release — a shorter drop that finishes the job. Attach a project to a chat and its pinned items and sources now travel the same four-phase retrieval pipeline as everything else. And the knob that caps knowledge searches no longer eats the agent's whole turn: tool steps and retrieval calls are two separate budgets.

Project knowledge, now agentic

Attach a project — its pins and sources flow through the full four-phase pipeline, not a side door.

Until now, project items were searched by a legacy side-channel tool: one flat hybrid search per context, capped at ten results, no reranking, no query expansion — and its own approval prompt. That tool is gone. Project knowledge now travels the same understand → search → rerank → verify-against-memory pipeline from part 1, so a spec pinned to a project is found with the same accuracy as any knowledge base the agent owns.

It works with zero setup, whichever kind of agent the chat runs on. An agent without knowledge search configured gets a pipeline instance injected automatically, scoped to the project. An agent with the search tool sees the project become an additional source inside its one configured pipeline — same routing rules, same vocabulary, same reranker.

One new switch on the wizard's Behavior step — "Search attached project items", on by default — controls the whole behavior per agent. And project custom instructions, which used to be stored but never reached the model, now feed the pipeline's routing. They're gated at execute time on that same switch, so turning it off genuinely turns all of it off.

Project retrieval mechanics

Pins, scoped sources, one pipeline — a project may add scope, but it never narrows what an agent already searches.

The invariant behind the design: attaching a project can only widen retrieval. Items living in sources the agent already searches become rerank pins — a relevance boost, never a filter, so the rest of the knowledge base stays reachable. Items in contexts outside the agent's configuration are added as item-scoped sources, searched with a hard filter to exactly the project's items. A bare context entry means the whole context — which, incidentally, used to silently return nothing and now works. And project-referenced sources are always routed as main sources: attaching a project is itself a relevance signal, so those sources are searched immediately rather than waiting on a weak first pass.

  • Legacy tool deleted — the per-project side-channel search (and its approval prompt) is gone; the pipeline tool needs no approval.
  • Pins vs scoped sources — already-searched sources get boosts; new contexts get item-scoped searches.
  • Always-main routing — project sources skip the backup queue.
  • Whole-context entries fixed — a context attached without item ids now searches the full context.
  • Project instructions live — custom_instructions now reach the pipeline's routing, gated on the switch.

The four phases themselves are unchanged from part 1 — the July 7 page walks through them. Note for self-hosters: project retrieval now runs on the agentic-retrieval pipeline, which requires the EE license.

Two budgets, decoupled

Retrieval calls no longer eat the turn budget — cap them separately, right on the agent.

Before this release, the wizard's step limit bled into the whole turn's budget: a retrieval cap of 3 meant the agent got three steps for everything. We hit this in production testing — two bash calls in, the agent was forced into a final answer before it had even searched. Now there are two separate knobs, and each caps exactly what it says.

"Max tool steps per message" is a new number field in the agent editor's Chat experience section. It caps all tool steps an agent may take on one message — bash, files, knowledge search, integrations — with 0 falling back to the platform default of 10. It's a plain agent field, so it travels with the agent everywhere.

The wizard's old limit is relabeled "Max knowledge searches per message" and now caps only agentic-retrieval calls. Once the search budget is spent, the search tool is silently dropped from the active tool set — every other tool keeps running until the turn budget is reached. The guard is enforced at every provider and gateway site, so API traffic behaves exactly like chat. Existing configs keep working unchanged; they just stop capping the whole turn.

GraphQL — the budget is a plain agent field
mutation UpdateAgentEditor($id: ID!, $max_tool_steps: Float) {
  agentsUpdateOneById(
    input: { max_tool_steps: $max_tool_steps }
    id: $id
  ) {
    item {
      id
      name
      max_tool_steps
    }
  }
}

Final-step hardening

Budget-exhausted turns end in prose — a real answer, or an honest account of where the agent got to.

When an agent runs out of tool steps, Exulu forces a final plain-text answer: tools are stripped and the turn's tool history is flattened into text. In production testing we caught a model imitating the flattening itself — the history rendered tool calls as [called tool bash: {...}], and the model's "answer" was a new line in exactly that bracket format instead of prose.

The flattened history is now written as plain prose — "Earlier, the assistant ran the bash tool with input: …" — so no copyable call-syntax template remains anywhere in the final step's context. The final-step instruction is equally explicit: answer in normal prose, never output tool-call syntax or bracketed lines, and if the step limit was reached, say so honestly, summarize progress, and name what remains. The guard is three layers deep — tool choice forced off, active tools emptied, prose-flattened history with the explicit instruction — each layer added after the previous one failed in production testing.

The result: a turn that hits its budget reliably ends in a real answer, or an honest "I hit the step limit, here's where I got to" — never machine-shaped noise.
