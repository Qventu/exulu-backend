Release · July 8, 2026

The context wall comes down.

Long sessions used to die at the model's context limit — phantom token totals, raw provider errors, work lost mid-thought. Exulu now measures real context occupancy, compacts history on your terms, and offloads oversized content automatically — for every model, on every surface. You watch it happen, and you steer it.

The honest context meter

Context occupancy and lifetime spend are finally two different numbers — no more phantom 21M-token readings.

The usage chip in the chat header used to add up token usage across every turn — and because each turn's input already contains the whole conversation so far, the total grew super-linearly. Long sessions reported figures like 21 million tokens against a 128K model, sometimes sailing past 100%. Alarming, and wrong.

The chip now shows real context occupancy: the newest usage number actually reported by the provider (or the latest compaction checkpoint), plus a light estimate of everything after it, over the model's usable window — its context window minus the space reserved for the reply. Click it and the popover separates the two ideas cleanly: Context window up top, with a progress bar for what the model sees right now, and Session usage (cumulative) below it for what the conversation has spent in total.

The 80% warning color keys off real occupancy, so amber means something again. And if you override the model for a session, the meter resolves that model's own window from the catalog — switching to a smaller model tightens the meter automatically.

Compact, don't restart

One click summarizes older history into a checkpoint — steerable, visible, and nothing is deleted.

At 80% of the usable window, an amber banner appears above the composer — "Approaching the context limit" — with a Compact conversation button and an optional steering input. Compaction never happens behind your back: you trigger it, and you can tell it what matters — "keep the exact figures from the service reports" — so the summary preserves in detail exactly what you'll need later.

One click runs a single deterministic summarization call over everything before a verbatim tail of recent messages, and inserts the result as a checkpoint. From then on the model sees checkpoint + tail; the full history stays in the database and in your thread, where the checkpoint renders as an expandable divider — "Summary (78K → 2.2K tokens)" — and the meter drops on the spot.

The endpoint is a first-class sibling of the run route, so anything driving Exulu over REST can compact a session too. It refuses politely while a response is still streaming, and in the rare case where even compaction can't make the conversation fit, a structured error says so — with "start a new chat" guidance instead of a cryptic failure.

Compact any session over REST
curl -X POST "$BACKEND/agents/litellm/compact/$AGENT_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Session: $SESSION_ID" -H "User: $USER_ID" \
  -H "Content-Type: application/json" \
  -d '{"steer": "keep the exact figures from the service reports"}'
# → { "checkpoint": { …UIMessage with metadata.compaction… },
#     "occupancyEstimate": 8400, "originalTokens": 78031, "summaryTokens": 2210 }

A hard stop before the model breaks

At 95% the composer blocks — and the server enforces the same limit on its own.

When occupancy crosses 95% of the usable window, the chat stops accepting input instead of letting the next request fail: the banner switches to "Context limit reached" and can no longer be dismissed, the textarea disables with a new placeholder — "Compact the conversation to continue…" — and the send button greys out. The fix stays one click away: Compact conversation is right there in the banner.

The same gate runs server-side before every model call, so an oversized request is never sent to a provider — API callers get a structured 413 instead of a crash. And provider context-length errors that slip through mid-stream ("maximum context length", "prompt is too long", LiteLLM's ContextWindowExceededError, …) are pattern-matched and rewritten to the same code, so every possible overflow lands in the same recoverable state. You'll never see a raw context error again.

Tool outputs: capped, saved in full, paged back

An 84,000-token web search no longer eats the conversation.

A single guard now wraps the output of every tool — built-ins, MCP servers, agents-as-tools, web search — with one deliberate exception for agentic retrieval, whose pipeline already bounds itself. Results under the cap (10% of the context window, between 4K and 25K tokens) pass through untouched. Over the cap, the full output is written to a session file — it shows up in the Session files panel like any other file — and the model receives a short preview plus a notice naming the file and the escape hatch.

That escape hatch is read_session_file, a new tool that pages any session file by line range — default 250 lines, with a hard slice cap so a read can never blow up the very context it exists to protect. The system prompt teaches the model the convention, so it pages through the stored output on its own instead of asking you to repeat yourself. Nothing is thrown away; it's just moved somewhere the agent can read at its own pace.

Large uploads become retrievable corpora

Upload as much as you like — each turn only pays for the parts the agent actually needs.

This release started with a real incident: a user uploaded 89 service reports, and every subsequent turn re-sent roughly 1.3 million input tokens of extracted document text — until requests died with raw provider errors. Text extracted from uploads now flows through the same cap as tool outputs, right at the extraction point.

Oversized extractions keep their first ~4,000 characters inline, followed by a notice the model understands:

[Document "<filename>" truncated: ~184,000 tokens. The full extracted text is saved as session file "<name>" — read specific parts with read_session_file (offset/limit).]

The full text is stored as a session file and appears in the Session files panel, same as any upload. And the agent knows what to do with it: the system prompt explains that oversized content lives in named session files and should be paged with read_session_file rather than re-requested. A big upload stops being ballast the model re-reads on every turn and becomes a corpus it queries on demand — and nothing you uploaded is ever lost.

Guards while the agent is working

The turn that explodes mid-flight is handled too — silently, on every surface.

The 80% and 95% thresholds cover conversations that grow between turns. But an agent can also blow its budget inside a single turn — a step loop calling tool after tool until the accumulated results no longer fit. A new in-flight guard tracks estimated context during the loop, and when a turn crosses the usable window it collapses tool results in all but the two most recent tool messages down to a short stub pointing at the stored session file. No failed request, no user interaction — the turn just keeps going, and everything collapsed stays readable via read_session_file.

The OpenAI-compatible gateway gets the same protection. Requests are pre-checked against the model's real budget, so oversized prompts get a proper OpenAI-style error instead of a provider crash — and the gateway's step loop runs the same in-flight guard. Continue.dev, Cowork, routines: every surface without a chat UI benefits without changing a line.

One budget, every model

Every number on this page comes from one module — mirrored byte-for-byte on client and server.

Underneath it all sits a question the platform can finally answer precisely: how big is this model's context window, really? The backend now resolves the actual figure at runtime — from the LiteLLM catalog or the provider's own declaration, falling back to a logged default only for unknown models. Before this, every runtime consumer assumed 128K: too big for small models, too small for million-token ones. Session model overrides are respected too, so pinning a chat to a smaller model automatically tightens every guard above.

From that one window, a single module derives the entire budget — and the frontend mirrors the same formulas byte-for-byte, so the meter, the banner, and the server gate can never disagree. Occupancy self-corrects as well: it re-anchors on the provider's real usage report every turn, so estimate drift never accumulates.

History is finally deterministic, too. Sessions now load in full, ordered by creation time — the old code fetched 50 messages with no ordering at all, so long sessions sent the model an arbitrary subset — while compaction checkpoints keep the assembled prompt bounded as checkpoint + everything after it.
