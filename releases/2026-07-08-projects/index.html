Release · Projects

A home for every piece of work.

Projects are named, private workspaces that keep a team's chat sessions, pinned knowledge and shared files together — with a knowledge scope every session in the project inherits, and access controls and a configurable cascade delete when it's time to clean up.

Files tab

Pin the knowledge. Every session inherits it.

The project detail page is a workspace, not a form. Under the header — breadcrumb "Projects /", avatar and name, and a purple "New session" — sit three URL-backed tabs: Sessions, Files, Settings (?tab=, refresh-safe and back-button-steppable). The Files tab is the curation surface for a project's pinned knowledge, and pinning is the whole point: "Pin knowledge items to share them with every session in this project."

A mini-toolbar shows a live "{count} / {max} files" counter (e.g. "2 / 15 files") next to an outline "Add files" button, and the Files tab trigger carries a small secondary "2/15" badge. The shared ItemsSelectionModal does the picking — a Browse tab (folder tree → items list with a purple checkbox select state → a right-hand "Selected Items" rail) and a Presets tab. Confirm reads "Add (1) Item"; the modal closes, a new ProjectItemCard fades and scales in (200 ms), and the counter ticks "2 / 15 files" → "3 / 15 files". Each card shows the item name (linking to /data/{context}/items/{id}), a description, and a footer of context · relative-time · N chunks.

There are three add paths but one cap: pick individual items, pick a whole "Entire context", or apply a saved preset — each is atomic against 15. An over-cap batch applies nothing and says how many slots remain ("Only # slot(s) left — nothing was added."); at the limit the button disables with "This project has reached the limit of 15 files. Remove one to add another.". Two edge cases stay honest: a full-context pin renders a distinct Database-icon card with an "Entire context" badge, and a deleted item renders a muted dashed "Item no longer exists" card that stays removable — orphans are never silently dropped.

GraphQL — every confirm writes the pinned gid list — project_items — to the project:
mutation UpdateProject($id: ID!, $input: projectInput!) {
  projectsUpdateOneById(id: $id, input: $input) {
    item {
      id
      name
      project_items
    }
  }
}

Projects index & create dialog

Named, private workspaces for your team's AI.

The /projects index is now a standard collection page (the old permanent ProjectNav sidebar and projects/layout.tsx are gone; switching happens here or via ⌘K). Its PageHeader carries an h1 "Projects", the description "Workspaces that group your conversations and shared context.", and exactly one primary action — a purple "New project" button that replaces the old cryptic icon-plus.

Creating one is a single dialog ("Create new project" — "A project groups chat sessions and shared files in one place."): a Name and a Description field are visible, custom instructions tuck inside a collapsed "Advanced" section, and a Lock-icon trust line states the promise at the moment of creation — "Private — only you can see this project until you share it.". Clicking the purple "Create project" button submits with rights_mode: "private", toasts "Project created.", and navigates straight into the new workspace.

The payoff is the real project detail header: a breadcrumb "Projects / Quarterly report", avatar and name, a "Private" visibility badge (Lock pill), and the purple "New session" action. No intermediate confirmation screen — you land on the Sessions tab of a project that is already yours alone, and sharing is a later, explicit step in Settings → Access.

GraphQL — create dialog fires one mutation — private by default:
mutation CreateProject($input: projectInput!) {
  projectsCreateOne(input: $input) {
    item {
      id
      name
      rights_mode
    }
  }
}

Your workspaces, starred and searchable

A standard collection page — favorites pinned, search on the server, nothing hidden past 200.

Starred projects pin to the top under a "Favorites" heading (then "All projects") and appear exactly once — the group hides while searching so a project never shows up twice — while the star itself is a FavoriteToggle with aria-pressed that pops on tap (a 200 ms zoom-in-50, reduced-motion safe) and, because rows are stretched links, calls preventDefault/stopPropagation so starring never navigates. Favorites are one shared source of truth across the list, the detail-header star, and re-navigations; a failed toggle reverts only the toggled project and toasts "Couldn't update favorites. Please try again.".

The single Toolbar search ("Search projects…") filters on the server through GET_PROJECTS with a name contains filter rather than a client scan — an empty result reads "No projects found" / "Try a different search term." — and past the 200-row window a ghost "Load more" button appears whenever hasNextPage is true, so the old silent 200/50 ceiling finally has a visible affordance. With no projects at all, the empty state reads "No projects yet" / "Projects keep related conversations and files together.".

Sessions tab

Start, remove, undo — the work, not the paperwork.

The Sessions tab is the L1 surface of a project — "a place you work" — with each row resolving its agent's real name client-side (while unresolved or if the agent was deleted it renders nothing, never a raw id) and a title that stretches into chat's existing /chat/[agent]/[session] route. "New session" opens an agent picker whose description preserves the trust disclosure "Choose an agent for the conversation. Sessions started in a project can be viewed by project members."; picking an agent fires CREATE_AGENT_SESSION with project: <id> and rights_mode: "private", then jumps straight into the new chat.

Each row's overflow menu carries two RBAC-gated actions (disabled with "You don't have write access to this session" when the user can't write): "Remove from project" detaches immediately and offers an "Undo" toast ("Session removed from project.") that re-attaches the same session, while "Delete session…" runs through the shared ConfirmDialog ("Delete session?" / ""{title}" will be permanently deleted. This cannot be undone.") and, once confirmed, collapses the row over 300 ms before the list reflows. Untitled sessions fall back to "Untitled session", and "Load more" appears past the 50-session window.

Settings tab

Details, access, and a delete you configure with your eyes open.

The Settings tab consolidates the legacy "Project information", "Access control" and "Project settings" views into three quiet sections — Details · Access · Danger zone — with only the danger zone carrying a destructive border. Details edits name, description and the custom instructions every session inherits (in read mode the header shows a quiet "Instructions active · View" line that deep-links here), and Access drives an RBACControl across private / users / roles whose save reports success or error via toast ("Access rights saved.") — Details and Access each own their own UPDATE_PROJECT hook so the two save spinners no longer animate each other.

Deleting a project is a cascade you configure with your eyes open: the shared ConfirmDialog ("Delete project?" / ""{name}" will be permanently deleted. This cannot be undone. Sessions you don't delete are kept and detached from the project.") offers checkboxes "Also delete all files" and "Also delete all sessions" whose counts are live — files from the current pinned list, sessions from pageInfo.itemCount, not just the loaded rows — and an amber warning recomputes per selection: "# files and # sessions will be permanently deleted with the project.". The cascade walks all session pages, not the 50 loaded rows, so no session is stranded pointing at a deleted project id; on success it toasts "Project "{name}" has been deleted." and routes back to /projects.
